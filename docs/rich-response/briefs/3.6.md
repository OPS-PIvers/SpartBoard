## 1. Goal

Let a student hear their own recorded answer back, but only after the teacher
has published results for that assignment, and only for their own response. No
playback exists before submit-and-publish; before submit, review is local/free
(already covered by the capture flow — out of this brief's scope). Provisional
scores must be visibly marked in the same view.

## 2. Decisions to honor

**No student access before publish; playback on the published-results screen,
gated on the teacher publishing.** Three windows: before submit, review is
local/free (capture flow's territory, not this brief's). After submit and
before publish, **no access at all** — the Firebase transit copy is gone within
minutes (Brief 3.3) and the Drive copy is teacher-owned. After the teacher
publishes results, the recording plays back **for its owner**
(`docs/rich-response-wayfinder.md:828-842`).

**The gate is a callable that verifies (a) requester uid === the response's
`studentUid`, and (b) results are published for that assignment** — bounded
three ways: published assignments only, owning student only, on demand only
(`docs/rich-response-wayfinder.md:843-849`). This is an **explicit teacher
act** gating disclosure, not a standing exposure — reject any design where the
student can fetch a Drive link independent of this callable's verification
(`docs/rich-response-wayfinder.md:846-849`).

**Rejected alternatives, do not build them:** grade-and-comments without
playback (unusable feedback on a 90-second spoken answer the student can't
hear — `docs/rich-response-wayfinder.md:851-852`); playback on demand
regardless of publish state (`:853-855`).

**No public Drive sharing link.** The archived file in Drive is **not** made
public (unlike the Activity Wall photo precedent, which calls
`makeDriveFilePublic` — Brief 3.3 explicitly does **not** do that for quiz
media). Playback must be proxied/streamed through a server-verified callable
using the teacher's stored refresh token — the same
`refreshGoogleAccessTokenForUid` mechanism used for archival
(`docs/rich-response-wayfinder.md:706-730, 843-849`), not a public `lh3`-style
URL. (`lh3.googleusercontent.com/d/{fileId}` links, used by
`archiveActivityWallPhoto`, only work for **public** files and only serve
**images** — `docs/rich-response-wayfinder.md:672-673` — neither property
applies here.)

**Provisional scores are marked student-side too.** A response with any
`GradeResult.state !== 'scored'` slot must show a provisional indicator rather
than a bare final number, mirroring what Brief 3.4 does teacher-side
(`docs/rich-response-wayfinder.md:1776`, sub-decision 8: "never a bare number,
in the live monitor, the results list, the export **and the student's
published view**"). This applies even when the recording slot itself hasn't
been played — the student sees their score is provisional whether or not they
press play.

**Playback works for whatever the student can hear regardless of `gradedTakeIndex`
pinning.** RR-06 sub-decision 4 lets a teacher grade an earlier take than the
one scoring reads (`docs/rich-response-wayfinder.md:1772`). The student's
published-results view should play the **take the grade is about**
(`gradedTakeIndex` if the grade carries one, else the highest `takeIndex` /
scoring winner) — showing the student a recording that doesn't match the
comments they're reading would be confusing and undermines the entire reason
`gradedTakeIndex` exists ("which sixty seconds was this about,"
`docs/rich-response-wayfinder.md:1772`).

**Time-anchored comments render against the played take.** If Brief 3.4 has
shipped time-anchored `WrittenAnswerAnnotation`s (`from`/`to` in ms) for the
graded take, this view should render them as markers on the playback UI (the
same visual language the teacher's grading view uses, reused not
reinvented) — if Brief 3.4 hasn't landed yet, render the audio player alone
with no annotation markers and treat that as an acceptable interim state, not
a blocker.

## 4. Step-by-step implementation notes

Design language: light mode per `CLAUDE.md` "Design Context" (student-facing
surfaces are light, not dark glass) — match `PublishedScoreReview`'s existing
styling exactly; do not introduce a new visual language for the new playback
control.

1. **New callable**, recommend `functions/src/getQuizArtifactPlaybackUrl.ts`
   (or add to a shared `quizMediaArchive.ts` if Brief 3.3 created that file —
   check first). Signature: `{ sessionId, questionId, slot }` (identify the
   artifact by question+slot rather than raw artifact id, since the student
   shouldn't need to know internal ids — the callable resolves the artifact
   id server-side from the response). Steps:
   1. `request.auth` required; derive `studentUid = request.auth.uid`.
   2. Load the session doc; **verify `scoreVisibility` is set and not
      `'none'`** (the exact same field `publishAssignmentScores`/
      `unpublishAssignmentScores` write — read the session doc directly,
      don't trust anything client-supplied).
   3. Load the response doc at `responses/{responseKey}` where
      `studentUid` matches `request.auth.uid` (do **not** trust a
      client-supplied `responseKey` blindly — resolve it the same way the
      student's own client would, or accept `responseKey` but verify
      `response.studentUid === request.auth.uid` before proceeding, exactly
      mirroring the existing rules pattern for response ownership).
   4. Find the answer entry for `questionId`; find the artifact for `slot`.
      Resolve which take to play: if `response.grading[gradingKey]?.
gradedTakeIndex` is set (Brief 3.4's field, if it exists — treat as
      optional/absent gracefully if Brief 3.4 hasn't landed), use the answer
      entry with that `takeIndex`; else use the entry with the highest
      `takeIndex` among entries for that `questionId`.
   5. Look up `artifactArchive[artifactId]` (Brief 3.3's sibling map). If
      `archiveStatus !== 'archived'` or `driveFileId` is missing, return a
      clear "not available yet" response (not an error) — a student
      shouldn't see a broken player for a take still mid-archive.
   6. Load the **teacher's** uid from the session doc (`teacherUid`); call
      `refreshGoogleAccessTokenForUid(teacherUid)`.
   7. Fetch the file bytes from Drive
      (`GET .../files/{driveFileId}?alt=media`, `Authorization: Bearer
{accessToken}`) and stream them back through the callable's HTTP
      response, **or** (cheaper, and matches how `onCall` callables
      typically return data) fetch the bytes server-side and return them
      base64-encoded if small enough (audio takes are ≤ ~1.2 MB at the
      caps set in Brief 3.3 — base64 inflates ~33%, still comfortably under
      Cloud Functions' response size limits). **Do not return a bare Drive
      URL or access token to the client** — that would hand the student (or
      anyone who inspects network traffic) a bearer credential to the
      teacher's Drive file; the whole point of proxying is that the token
      never leaves the server. Recommend: `onRequest` (HTTPS, not `onCall`)
      so the browser's `<audio>` element can use the URL directly with
      range-request support for scrubbing — an `onCall` callable can't be an
      `<audio src>`. If using `onRequest`, verify the Firebase ID token
      manually from an `Authorization` header (see `functions/src/embedProxy.ts`
      if it exists — check for a precedent of an authenticated `onRequest`
      proxy pattern already in this codebase — grep for `onRequest` usage
      across `functions/src/*.ts` before inventing a new pattern) and apply
      the same CORS allowlist (`ALLOWED_ORIGINS` from
      `functions/src/classlinkShared.ts`, already imported by
      `driveArchive.ts:10`).
2. **Client hook**, recommend a small addition to whatever hook
   `QuizStudentApp.tsx` already uses for results data (or a new
   `hooks/useQuizArtifactPlayback.ts`) that calls the callable/endpoint from
   step 1 lazily — only on the student pressing play for a given
   question/slot, not prefetched for every recording question on page load
   (bandwidth + avoids needless Drive API calls for takes the student never
   listens to).
3. **UI in `PublishedScoreReview`.** For each rendered question row that has
   an audio artifact (check `artifacts` on the corresponding answer, filtered
   to `kind === 'audio'`), render an inline `<audio controls>` (or a custom
   player if the design calls for one — keep it simple, native controls are
   fine and accessible by default) that lazy-loads its `src` via step 2's hook
   on first interaction. Show a loading state while the callable resolves, and
   a clear "not available" state if step 4.5 (archival not finished) or any
   error occurs — never a silently broken `<audio>` tag.
4. **Provisional marking.** Wherever `PublishedScoreReview` renders the
   top-level score/percentage, check whether any answer's underlying
   `GradeResult.state !== 'scored'` (this likely requires the same per-slot
   `GradeResult` computation logic Brief 3.4 introduces — reuse it, don't
   duplicate; import from wherever Brief 3.4 puts it, or if that logic isn't
   extracted into a shared util yet, do that extraction as part of this
   brief and note it for Brief 3.4 to reuse too). If any slot is not yet
   `scored`, render a "provisional — your teacher hasn't finished grading
   everything yet" badge/note next to the score, matching whatever visual
   convention Brief 3.4 established teacher-side (badge/asterisk + tooltip).
   If Brief 3.4 hasn't landed and no per-slot `GradeResult` computation
   exists yet, fall back to: any question with an audio artifact and no
   `grading[key]` entry at all → treat as provisional. Document this
   fallback clearly in a code comment so it's replaced once Brief 3.4 lands.

## 5. Backward-compatibility constraints

- No change to `PublishedScoreReview`'s existing three-mode disclosure logic
  (`score-only`/`score-and-responses`/`score-responses-and-answers`) — the
  playback control is additive, rendered only when a question actually has an
  audio artifact, and only within whichever disclosure mode already shows
  that question's row.
- No change to `publishAssignmentScores`/`unpublishAssignmentScores` — this
  brief only **reads** `scoreVisibility`, it doesn't write it.
- **No `firestore.rules` change needed.** The existing owning-student read
  rule on `/responses/{responseKey}` already covers everything this brief's
  callable reads from Firestore (§3). Verify this by reading the full current
  rule block before finalizing — if it turns out the rule scopes reads more
  narrowly than assumed (e.g. field-level restrictions), flag it under a
  "Protected-file change needed" heading instead of editing rules directly.
- **No `storage.rules` change needed** — this brief never touches Firebase
  Storage; media is served from Drive via a server-side proxy.
- The new callable/endpoint must fail closed: any Firestore read error, any
  missing field, any ambiguity about publish state → deny playback, never
  default to allowing it.
- Adding `getQuizArtifactPlaybackUrl` (or equivalent) to
  `functions/src/index.ts`'s exports is additive; no existing export changes.

## 7. Acceptance criteria

- [ ] A student cannot fetch/play a recording before the teacher publishes
      results for that assignment (server-verified, not client-gated only).
- [ ] A student can only play their **own** response's recordings, never a
      classmate's, even with a forged `responseKey`.
- [ ] No public Drive link or bearer token is ever sent to the client; the
      access token never leaves the server.
- [ ] Playback resolves to the graded take (`gradedTakeIndex` if present,
      else highest `takeIndex`), not always the newest recording.
- [ ] A take stuck mid-archive shows a clear "not available yet" state, never
      a broken player.
- [ ] Any provisional (not-yet-fully-graded) response shows a provisional
      marker next to its score, not a bare number.
- [ ] Unpublishing results (`unpublishAssignmentScores`) immediately revokes
      playback with no separate cleanup — verified by the callable re-reading
      `scoreVisibility` on every call rather than caching.
