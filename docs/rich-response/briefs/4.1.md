**Read `docs/rich-response/briefs/CONVENTIONS.md` before implementing** — it
carries this run's locked engineering conventions (branch/PR shape, machine
test-run limits, protected-file handling, i18n requirements for every new
UI string, "no `alert()`/`confirm()`" for the delete-confirmation flow this

## 1. Goal

Give a district (org) admin a screen that lists student media responses and
their takes across the organization, lets them delete a response's media and
any associated derived artifacts as one atomic operation, and executes those
deletes server-side against the owning teacher's Drive using the same stored
refresh-token mechanism the archival pipeline already uses — with no teacher
present. This is a **compliance precondition**: per the build order in
`docs/rich-response/IMPLEMENTATION.md` Phase 4, audio capture opens to
beta/public users only after this console exists; admin-gated testing may
precede it.

## 2. Decisions to honor

**This is a compliance precondition, not a feature — it ships before the first
media response does** (`docs/rich-response-wayfinder.md:1433-1435`). COPPA's
school-consent pathway rests on two conditions; only the second (giving the
school review-and-delete ability) is within SpartBoard's control, and this
console is what satisfies it (`:1113-1126, 1404-1435`).

**It resolves a real ownership collision: the durable copy lives in the
individual teacher's Drive, not anywhere org-admin-reachable.** RR-03 put
student media in the teacher's own Drive; COPPA's school-consent condition
requires giving the **district** review-and-delete ability. An org admin has
no standing over a teacher's personal Drive and SpartBoard holds `drive.file`
scope on the teacher's token only (`docs/rich-response-wayfinder.md:1404-1420`).

**The mechanism: reuse the stored, AES-encrypted refresh token at
`/users/{uid}/private/googleAuth`, Admin-SDK-only** — exactly what archival
already uses, so an org admin's delete executes server-side against _that
teacher's_ Drive with no new capability and no RR-03 amendment
(`docs/rich-response-wayfinder.md:1413-1417, 706-730`). Use
`refreshGoogleAccessTokenForUid(teacherUid)`
(`functions/src/googleOAuth.ts`) exactly as Brief 3.3's archival callable does.

**Rejected alternatives, do not build them:** a shared org Drive (reopens
RR-03, needs per-org shared-drive provisioning as a Workspace-edition
dependency, forfeits the district-lifecycle-bound retention promise —
`docs/rich-response-wayfinder.md:1426-1428`); an out-of-band support queue
(arguably literal compliance, but no audit trail, no scale
`:1428-1431`).

**A departed teacher's token is a known, accepted gap — not a bug to fix
here.** A departed/offboarded teacher's stored refresh token is simply dead;
that is district offboarding's territory, already the accepted answer on RR-03
(`docs/rich-response-wayfinder.md:820-826, 1418-1420`). The console must
**surface this honestly** (a delete attempt against a dead token fails
visibly, with a clear message — see §4) rather than silently no-op or claim
success.

**Deletes are "sets," not files — the console's own design problem to solve.**
Once takes append (RR-A2) rather than replace, a response can hold **multiple
takes per question per student**, and "delete this response" has to mean
something coherent when several takes exist
(`docs/rich-response-wayfinder.md:1537, 3459-3461`). This console decides that
shape (§4) — the map deliberately left it open.

**Derived artifacts are in scope of every delete, not just source media.**
COPPA § 312.2's "delete" standard reaches transcodes, transcripts, thumbnails,
and waveform data (`docs/rich-response-wayfinder.md:1166-1171, 1499-1503,
4141`). AI transcription is **not being built** (Paul, 2026-09-01 —
`docs/rich-response/IMPLEMENTATION.md`, "AI transcription is not planned"), so
in this brief's scope "derived artifacts" reduces to: the single transcoded
audio file archived in Drive (there is no separate "source" vs "transcode" —
Brief 3.3 transcodes once, on the way to Drive, and deletes the Firebase
transit copy immediately; by the time this console runs, the **only** copy is
the Drive file it deletes). Do not build transcript-deletion logic — there are
no transcripts.

**A delete request must not destroy records under an outstanding access
request.** § 99.10(e) forbids destroying records under a pending access
request; a sweep/delete flow "has to know about pending requests"
(`docs/rich-response-wayfinder.md:1173-1174, 1503, 4141`). **SpartBoard has no
concept of a "pending access request" today** — this is not something to
invent from scratch here. Handle it minimally: every delete from this console
requires an explicit admin confirmation step naming exactly what will be
destroyed (§4), which is the closest available safeguard; do not attempt to
build a formal legal-hold/pending-request tracking system as part of this
brief — flag it as a known gap in the acceptance criteria instead.

**Scope of "review":** list responses and takes; per RR-A2 sub-decision 8, the
teacher's own results view already plays takes and shows counts
(`docs/rich-response-wayfinder.md:3415-3421` — that's Brief 3.4's surface, not
this one). This console does not need its own playback UI to satisfy the
compliance requirement — listing metadata (student pseudonym or real name if
resolvable, question, take count, archive status, Drive file id, archived
date) is sufficient for "review." **Recommend adding playback here too** if
Brief 3.4's/3.6's Drive-proxy mechanism already exists by the time this brief
executes (reuse, don't duplicate), but it is not required for compliance —
note it as a nice-to-have in acceptance criteria, not a blocker.

**Retention/annual sweep is separate work.** This console is an
on-demand, admin-triggered tool. It is not the automated end-of-school-year
sweep (RR-04 sub-decision 6) — that is separate scheduled work outside this
brief's scope; this console's delete logic should be written as a reusable
function so that future sweep can call the same code path, but building the
scheduled sweep itself is out of scope here.

**Org-admin gating pattern: reuse the existing `Organization` panel's
`domainAdminOnly` convention**, not a new gate. This is district-facing
compliance tooling, which the codebase's existing role model already treats as
`domain_admin`-tier (see `RolesView.tsx`/`domains`/`roles` sections already
gated `domainAdminOnly: true` in `OrganizationPanel.tsx`).

## 4. Step-by-step implementation notes

Design language: dark glass per `CLAUDE.md` "Design Context" — this is an
admin surface; match `OrganizationPanel.tsx`'s existing chrome exactly (it
already uses the dark glass system).

**The hard problem this brief has to solve that the map left open:
how does an org-scoped admin screen find quiz responses, which are stored
per-user (`/users/{teacherUid}/...` for quiz metadata) and per-session
(`/quiz_sessions/{sessionId}/responses/{responseKey}` for response docs),
neither of which carries an `orgId`?** Read `functions/src/resolveOrgForUser.ts`
first — it's the existing mechanism for mapping a uid to an org. The realistic
approach:

1. Resolve the org's member list (teachers) via
   `/organizations/{orgId}/members` (already fetched by `useOrgMembers.ts` for
   the Users tab — reuse it).
2. For each teacher uid in that list, query
   `/quiz_sessions` where `teacherUid == <uid>` **and** the session has at
   least one response with a non-empty `artifactArchive` map. **This is
   expensive at scale (N teachers × a query each) and there is no existing
   collection-group index for "sessions with archived media."** Recommend:
   have Brief 3.3's archival callable (or this brief, extending it) write a
   lightweight denormalized index doc at write time —
   `organizations/{orgId}/mediaResponseIndex/{sessionId}_{responseKey}` (or
   similar) containing just `{ teacherUid, studentUidHash, questionId,
artifactCount, archivedAt, lastActivityAt }` — so this console reads one
   collection instead of fanning out. **This is a new Firestore write path
   this brief must add to Brief 3.3's archival callable** (or wherever
   archival happens) — call it out clearly in the PR/changes for Brief 3.3 if
   sequencing allows, or add it here defensively wrapped so it's a no-op if
   the field/index already exists. Document this index doc's shape in a code
   comment since nothing on the map specifies it.
3. `MediaReviewView.tsx` reads that index collection (scoped to the current
   `orgId`), renders a table: student (pseudonym, or resolved real name if a
   safe resolution path exists — do not build a new PII-resolution path here;
   reuse whatever `getPseudonymsForAssignmentV1`-equivalent already exists
   teacher-side, or show the pseudonym only if no safe resolver is callable
   from an org-admin context), question, quiz title, take count, archive
   status, archived date. Support filtering by teacher and by date range at
   minimum (a district records officer will be asked "everything from
   before X date" or "everything for teacher Y").
4. **Delete flow.** Selecting one or more rows and pressing "Delete" opens a
   `LocalModal` confirmation naming exactly what will be destroyed (student
   pseudonym, question, take count, "This will permanently delete N file(s)
   from {teacher}'s Google Drive and cannot be undone.") — this confirmation
   step is the accepted mitigation for the missing pending-access-request
   tracking (§2). On confirm, call a new callable (below) with the set of
   `{sessionId, responseKey, questionId}` (or artifact ids) to delete.
5. **New callable**, recommend `functions/src/deleteQuizMediaForOrgAdmin.ts`:
   1. `request.auth` required; resolve caller's org membership via the
      member-doc pattern from `organizationInvites.ts`; require `roleId` in
      (`domain_admin`, `super_admin`) for the **target** `orgId` (passed in
      the request, but cross-checked against the caller's actual membership
      doc — never trust a client-asserted role).
   2. For each target `{sessionId, responseKey, questionId}`: load the
      response doc, find every artifact for that `questionId` across every
      `takeIndex` (this is the "delete the set" behavior — §2's "sets, not
      files" requirement: deleting a question's media for a student removes
      **every take**, not just the latest), and for each artifact with an
      `artifactArchive[id].driveFileId`, call
      `refreshGoogleAccessTokenForUid(teacherUid)` (batch this per-teacher,
      not per-artifact, to avoid redundant token refreshes) and issue the
      Drive `DELETE`.
   3. On each successful Drive delete, update
      `artifactArchive[id]` to `{ archiveStatus: 'deleted', deletedAt:
Date.now(), deletedBy: request.auth.uid }` (new status value — extend
      `ArtifactArchiveEntry.archiveStatus`'s union from Brief 3.3 with
      `'deleted'`; leave `driveFileId` in place as a historical record of
      _what_ was deleted, do not clear it). **Do not delete the
      `QuizResponseAnswer`/`artifacts[]` entry itself** — the student's
      answer record (`answer`, timestamps) is a separate FERPA-relevant fact
      from the media artifact; only the media and its archive-tracking fields
      are what COPPA's "delete" obligation reaches. Note this as a judgment
      call in the PR description since the map does not explicitly decide it.
   4. **A dead/revoked teacher token** (the accepted gap from §2): if
      `refreshGoogleAccessTokenForUid` throws `needs-consent`, do **not** mark
      the artifact as deleted (it wasn't) — mark it
      `{ archiveStatus: 'delete-failed', archiveError: 'Teacher's Google
account is disconnected; the file cannot be deleted remotely.',
deleteAttemptedAt: Date.now() }` and surface this clearly in the
      response so the admin UI can show "could not delete — teacher
      offboarded" rather than a false success. This is the honest failure
      mode §2 requires.
   5. Return a per-item result array (`{ artifactId, status: 'deleted' |
'failed', error? }`) so the UI can show partial success accurately —
      a batch delete across many takes/students should not be all-or-nothing
      from the caller's perspective, since a single dead teacher token
      shouldn't block deleting everything else in the batch.
6. **Update the index doc** (step 2's denormalized collection) to reflect
   `deleted`/`delete-failed` status so the console's list view reflects
   reality without re-querying every artifact.

## 5. Backward-compatibility constraints

- `ArtifactArchiveEntry.archiveStatus` gains a new union member (`'deleted'`,
  possibly `'delete-failed'`) — additive; every existing reader of that field
  (Brief 3.3's callable, Brief 3.4's grading UI, Brief 3.6's playback gate)
  must treat any status other than `'archived'` as "not currently playable,"
  which they should already do by construction (only `'archived'` +
  `driveFileId` present means playable) — verify this holds rather than
  assuming, since Briefs 3.4/3.6 were written before this status value
  existed.
- The new `organizations/{orgId}/mediaResponseIndex/{...}` collection is new
  and additive; no existing reader is affected.
- **Protected-file change needed — `firestore.rules`:** add a new rule block
  for the index collection, org-admin-read-only, server-write-only:

```
match /organizations/{orgId}/mediaResponseIndex/{docId} {
  allow read: if request.auth != null &&
    isAdmin() || isOrgDomainAdmin(orgId, request.auth.token.get('email', '').lower());
  allow write: if false; // Admin SDK only (Cloud Functions)
}
```

(`isOrgDomainAdmin(orgId, emailLower)` should be a helper function reading
`/organizations/{orgId}/members/{emailLower}.roleId` — check whether an
equivalent helper already exists in `firestore.rules` for the existing
`Organization` panel's other admin-only collections, e.g. near wherever
`roles`/`domains` subcollection rules live, and reuse its exact name/logic
rather than inventing a new one with different semantics.)

- **No `storage.rules` change needed** — this console never touches Firebase
  Storage.
- The new callable is additive to `functions/src/index.ts`'s exports; no
  existing export changes.
- This brief does not alter `firestore.indexes.json` unless the index
  collection's filter/sort combination (teacher + date range) requires a
  composite index — check with the emulator/deploy error before assuming one
  is needed; if one is, add it under a "Protected-file change needed" heading
  rather than editing directly.

## 7. Acceptance criteria

- [ ] A `domain_admin`/`super_admin` for an org can see a list of student
      media responses across every teacher in that org, without needing each
      teacher's cooperation.
- [ ] The list survives being asked "everything for teacher Y" / "everything
      before date X" (basic filters).
- [ ] Selecting a response's media and confirming delete removes **every
      take** for that question/student from the teacher's Drive, not just the
      latest.
- [ ] A delete against a teacher whose Google connection is dead surfaces a
      clear per-item failure, never a false "deleted" success.
- [ ] The confirmation dialog names exactly what will be destroyed before any
      delete executes.
- [ ] No client ever receives a Drive access token or bearer credential; all
      Drive calls happen server-side in the new callable.
- [ ] A non-admin, or a domain_admin of a **different** org, cannot invoke the
      delete callable against this org's data.
- [ ] `QuizResponseAnswer`/`artifacts[]` entries are never deleted by this
      console — only `artifactArchive` status and the underlying Drive file.
