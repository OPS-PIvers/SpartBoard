## Owner notes (2026-09-01)

Scoping down to sweep-write + completeness predicate is accepted. The
required-slot authoring field arrives with 3.1's recording block; 2.2 must

## 1. Goal

Add the `unresponded?: UnrespondedReason` field to `QuizResponseAnswer`, make
the idle-finalize sweep write it for questions left empty at finalization,
and build **one** completeness predicate (binary for the student, richer for
the teacher) that later screens can route through instead of inventing their
own "is this answered" check. **Important scoping note, worked out in §2:**
the map's full design (required-addendum slots, the hard submit block,
`capture-unavailable`) depends on a "required addendum" concept from RR-01/
RR-02 that has **no authoring surface yet** (brief 3.5's job) — so this
brief builds the schema and the two concretely-buildable pieces (the sweep
write, the predicate utility) without inventing a submit-blocking UI that
has nothing to block on yet.

## 2. Decisions to honor

**RR-08 sub-decision 1 — every question the student leaves behind writes an
entry** (`docs/rich-response-wayfinder.md:2217-2235`):

> Absence now means exactly one thing: the student hasn't got there yet...
> Only a write carries the fact. The codebase already depends on this being
> true — `types.ts:365-371` [now `:380-405`, see §3] documents
> `pointsByQuestionId` as keyed by qid "so a missing entry means unanswered
> unambiguously," which only holds if nothing else can produce a missing
> entry.

Rejected: fixing only the one broken predicate
(`hooks/useQuizSession.ts`'s `'auto'`-mode stall) and leaving the other
~nine presence-based consumers unable to distinguish "passed over" from
"never reached." Rejected: writing an entry only for the `auto-advance`
case — makes "is there an entry?" depend on which of four authored values
(brief 3.1's `recording.prepExpiry`) a teacher picked, an invariant nobody
could hold in a mixed assignment.

**RR-08 sub-decision 2 — two axes, two fields; `status` untouched**
(`:2237-2273`):

```ts
interface QuizResponseAnswer {
  // ...unchanged
  status?: 'draft' | 'submitted'; // finality — UNCHANGED, still two values
  unresponded?: UnrespondedReason; // NEW — absent means the student responded
}
```

`status` already carries finality (returnable vs final); it must not be
re-solved. The missing axis is "did the student respond at all." **Both
RR-A1 prep-expiry branches become expressible**: `auto-advance` writes
`{ status: 'draft', unresponded: 'passed' }`; `unanswered` writes
`{ status: 'submitted', unresponded: 'expired' }`. **The reason vocabulary
is illustrative, not final** — the map explicitly leaves it open and two
later tickets (RR-A2, RR-05) both declined to extend it, landing on:
`'passed' | 'expired' | 'abandoned' | 'capture-unavailable'`. **Do not add a
`'declined'` reason** — RR-A2 explicitly rejected one (there is no refusal
exit in the recording flow, so no moment would ever write it).

Rejected: a third `status` value `'passed'` — overloads finality with
provenance; one field cannot say "final, and never responded to" for both
RR-A1 branches at once. Rejected: inferring from emptiness
(`answer === '' && !artifacts?.length`) — that shape is already legitimately
reachable today (written-response NEXT is deliberately ungated, so a
student can submit a blank essay on purpose), and inferring from it
conflates "chose to submit nothing" with "never got the chance."

**⚠️ The cost, stated explicitly in the map and worth repeating here**
(`:2269-2273`): an optional sibling field is **invisible to every existing
reader**. Nothing forces the roughly-ten presence-based consumers to
confront it — they keep counting these entries as answered until each is
visited deliberately. This brief does not visit all ten (see §8); it visits
the ones concretely in scope for the sweep and the new predicate. **Brief
1.3 visits four export/aggregation sites specifically because this field's
existence breaks their contract** — read that brief if you land close to it,
the ordering dependency runs both ways (1.3 must ship before or alongside
this brief; see its own §2).

**RR-08 sub-decision 5 — the idle sweep marks empty required slots at
finalize, at zero read cost** (`:2312-2333`):

> `publicQuestions` lives on the session doc, and the sweep already
> batch-reads every parent session doc to skip paused and waiting ones. It
> is holding the requiredness data already and simply doesn't look at it.
> So on finalize it writes sub-decision 2's marker with reason `abandoned`
> into any required slot left empty.

**Consequence, explicit in the map**: "the marker now has two writers, the
client for the passed-over case and the server for the abandoned one. They
must agree on the vocabulary, and nothing in Firestore can enforce that."
This brief owns the **server** writer (the sweep); the **client** writer
(brief 3.1's `auto-advance`/`unanswered` branches) is out of scope here —
see §2's scoping note below and §8.

**RR-08 sub-decision 7 — one completeness predicate; binary for the
student, three states for the teacher** (`:2364-2388`):

> A question is complete iff every required slot is filled... The indicator
> and the submit gate must be the same predicate, or the student cannot act
> on what they're being told... The teacher's monitor gets the richer view —
> answered / started-but-incomplete / never-reached — because "stuck on the
> recording" and "hasn't got there" demand opposite interventions.

⚠️ **This is a new state, not a refinement** — "partially answered" exists
nowhere in the shipped codebase today (not in `GradeResult`, not in
`QuizResponseAnswer`, not in the rules, not in a single UI string). Rejected:
three states for students too (stressful wording on a clocked assessment
when the cause is a broken microphone). Rejected: binary everywhere (throws
away the one distinction the teacher most needs live).

**Scoping note — the "required slot" half of this predicate has no
authoring surface yet.** RR-08's full design assumes a required-addendum
concept (RR-01: a primary response-mode set plus an optional, teacher-markable-required
addendum) that lives in `QuizQuestion` config. **Verified against the
current tree: no such field exists yet** (`QuizQuestion` at `types.ts:3144-3202`
has no response-mode or addendum-requiredness field; `QuizPublicQuestion`
at `types.ts:3375-3407` likewise has none). That authoring surface is brief
3.5's job, gated on brief 3.1's `recording` config block existing first.
**Until it lands, every authored question in the shipped model is
implicitly "required" in the only sense that currently exists** — a
question either has an `answers[]` entry or it doesn't; there is no partial
slot-filling concept for MC/FIB/Matching/Ordering/short/essay today. So this
brief's completeness predicate, for now, **degenerates to "does this
question have a non-`unresponded` entry"** — which is still real, useful
work (it's what makes the sweep-write and the progress-indicator fix
correct today), and it is explicitly designed to be extended, not replaced,
once brief 3.5 adds a per-question required-slot count. Do not attempt to
build the required-addendum concept in this brief; do not block this brief
on it existing.

**RR-08 sub-decision 3, 4, 6 (submit block, no-text-fallback,
bounded-upload-block) are explicitly OUT OF SCOPE for this brief** — they
depend on the required-addendum concept and the recording flow (brief 3.1/
3.2) not yet existing. Noted here only so you don't accidentally build a
submit-blocking UI with nothing real to block on. See §8.

**RR-A1's stall, which sub-decision 1 fixes** (`:3061-3067`, `:3069-3075`):
`'auto'` session mode advances only when every student has answered, tested
by presence in `answers[]`. Two of RR-A1's four `prepExpiry` values
(`auto-advance`, `armed`) pass over a question without writing anything —
`armed` correctly writes nothing (student is visibly parked, not skipped);
`auto-advance` needed a write, which sub-decision 1 supplies. **This brief
does not implement the `prepExpiry` branches themselves** (brief 3.1) — it
only needs to exist so that when 3.1 lands, the client-side write it makes
uses a field this brief has already defined and a vocabulary this brief has
already settled.

## 4. Step-by-step implementation notes

1. **Add the type to `types.ts`**, near `QuizResponseAnswer`:
   ```ts
   /** Illustrative vocabulary, deliberately left open by RR-08; do not add 'declined' (RR-A2 explicitly rejected it — no refusal exit exists). */
   export type UnrespondedReason =
     | 'passed'
     | 'expired'
     | 'abandoned'
     | 'capture-unavailable';
   ```
   Add `unresponded?: UnrespondedReason;` to `QuizResponseAnswer`, with a
   one-line comment: "absent means the student responded" (per CLAUDE.md's
   one-line comment convention).
2. **Build the completeness predicate utility.** New file or an addition to
   an existing quiz-utils module (check whether
   `components/widgets/QuizWidget/utils/` already has a natural home before
   creating a new file):

   ```ts
   /**
    * Whether a question is "complete" for progress/gate purposes — today,
    * that means "has a real (non-unresponded) answers[] entry." Once
    * required-addendum slots exist (brief 3.5), this predicate is the
    * place to extend to per-slot completeness rather than each caller
    * reinventing its own check.
    */
   export function isQuestionAnswered(
     answers: Pick<QuizResponseAnswer, 'questionId' | 'unresponded'>[],
     questionId: string
   ): boolean {
     const entry = answers.find((a) => a.questionId === questionId);
     return !!entry && !entry.unresponded;
   }

   /** Student-facing binary count: how many of `questions` are answered. */
   export function countAnsweredQuestions(
     answers: Pick<QuizResponseAnswer, 'questionId' | 'unresponded'>[],
     questionIds: string[]
   ): number {
     return questionIds.filter((id) => isQuestionAnswered(answers, id)).length;
   }
   ```

   Keep the teacher-side three-state richer view (answered /
   started-but-incomplete / never-reached) **out of this brief** — with no
   required-addendum concept yet, "started-but-incomplete" cannot currently
   occur (a question is either answered or not; there is no partial state
   until addenda exist), so a three-state function would have a dead
   branch. Leave a comment noting where it will hang once brief 3.5 lands,
   rather than building an unreachable state now.

3. **Route `QuizStudentApp.tsx`'s `answeredCount` through the new
   predicate**, replacing the raw `.length` at line 1016:
   ```ts
   answeredCount={countAnsweredQuestions(myResponse?.answers ?? [], /* all question ids for this student's served set */)}
   ```
   Determine the correct question-id list to pass by reading the
   surrounding context carefully — `myResponse?.answers` alone isn't the
   full set (a student may not have reached every question), so you need
   the served/public question id list this component already has in scope
   (check for `servedQuestionIds`/`publicQuestions`/similar props already
   threaded into this component before inventing a new one).
4. **Widen `finalizeIdleQuizAttempts.ts`'s `CachedSession`** (lines 311-314)
   to also carry `publicQuestions: QuizPublicQuestion[] | undefined` (or a
   minimal projection of it — just the `id` field is all this brief needs),
   extracted from the same batch-read session doc at line ~318-332 (no new
   Firestore read).
5. **In the per-doc finalize transaction** (lines 410-473), after building
   `finalAnswers`, compute the set of `publicQuestions` ids with no entry in
   `finalAnswers`, and append an `unresponded: 'abandoned'` entry for each:
   ```ts
   const answeredIds = new Set(finalAnswers.map((a) => a.questionId));
   const meta = sessionMetaBySid.get(sid); // already in scope
   const missingEntries = (meta?.publicQuestions ?? [])
     .filter((q) => !answeredIds.has(q.id))
     .map(
       (q): QuizAnswer => ({
         questionId: q.id,
         answer: '',
         answeredAt: finalizedAt,
         status: 'submitted',
         unresponded: 'abandoned',
       })
     );
   const allFinalAnswers = [...finalAnswers, ...missingEntries];
   ```
   Use `allFinalAnswers` (not `finalAnswers`) in the `update.answers`
   assignment. **Only do this when `finalAnswers.length > 0` OR always** —
   re-read the existing "don't consume an attempt slot for a student who
   joined but never answered" comment (lines 442-455) before deciding: that
   logic already special-cases the zero-answer case for the attempt-slot
   counter (`completedAttempts`), and this brief's addition should not
   interfere with it. The safest approach: compute `missingEntries`
   regardless, but only feed them into `update.answers` — do not let their
   presence flip `finalAnswers.length > 0` from false to true, since that
   would incorrectly consume an attempt slot for a student who genuinely
   never engaged. Check the `finalAnswers.length > 0` condition at line 463
   still reads the **real** answers count, not the count including the new
   synthetic `abandoned` entries.
6. **Keep `QuizAnswer` (the Cloud-Functions-local type in this file) in
   sync** with `types.ts`'s `QuizResponseAnswer` — add the same

7. **Do not build**: the client-side `auto-advance`/`unanswered` writers

   required-addenda existing), the required-addendum authoring UI (brief

## 5. Backward-compatibility constraints

- `unresponded` is optional. Every existing response document has none —
  `isQuestionAnswered` treats a present, non-`unresponded` entry as
  answered (today's exact behavior) and an absent entry as not answered
  (also today's exact behavior). The predicate is a no-op change in output
  for every legacy document; it only starts differing once something writes
  `unresponded`.
- The sweep change (§4 steps 4-5) is the **first** writer of `unresponded`
  in the whole codebase. It must not change `completedAttempts` counting
  behavior for the zero-answer case (see step 5's caution) — write a
  regression test asserting this explicitly (§6).
- No Firestore rules changes. The sweep already writes to `answers` via the
  Admin SDK (Cloud Functions bypass rules); adding a new field to entries it
  already writes needs no rule change. Verify `firestore.rules` is
  untouched in the diff.
- No Storage/index changes.
- `QuizAnswer` (Cloud Functions local type) and `QuizResponseAnswer`
  (`types.ts`) must be kept in sync by hand — there's no shared import
  between the two type surfaces (confirm this by checking the top of
  `finalizeIdleQuizAttempts.ts` for its type imports) — note this
  explicitly in the PR so a future edit to one doesn't silently diverge from
  the other.
