## 1. Goal

Build the per-question `recording` config block and the student-facing
capture flow for **audio only**: Tennessen notice → prep → armed → recording
→ hard stop, with a record → review → commit-or-discard loop before anything
is written to Firestore. This ships the data model and UI for the timing
model; takes/retakes are brief 3.2, authoring UI is brief 3.5, Drive
archival is out of scope (3.3), grading is out of scope (3.4).

Video is a peer mode in the data model (`kind: 'video'` on the artifact,
`'video'` in the response-mode set) but **no video capture UI, framing
check, or transcode path is built here**. Do not gate anything on video
existing — just don't build it.

## 2. Decisions to honor

**Timing model (RR-A1, resolution sub-decisions 1–8, `docs/rich-response-wayfinder.md:2996-3220`):**

- **Auto-start is a valid path.** RR-A1 sub-decision 1 (`:2999-3041`) restored
  auto-start after RR-04 briefly killed it — the Tennessen interstitial _is_
  advance notice, and institutional consent covers the rest. Do not build a
  "no timer path reaches the recorder" invariant as a hard rule; it was true
  only transiently.
- **Four authored `recording.prepExpiry` values** (`:3052-3059`), each a
  distinct behavior when prep time runs out:

  | Value          | Behavior at prep expiry                                                                                                                                                                              |
  | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `auto-start`   | Capture begins automatically. The record button becomes an early "start now."                                                                                                                        |
  | `auto-advance` | Move on; question stays open, returnable from summary. Writes `{status:'draft', unresponded:'passed'}` (RR-08 sub-decision 2 — see brief 3.2/3.5's shared dependency, but this brief must write it). |
  | `armed`        | Nothing happens; record button stays ready indefinitely. Writes nothing (correctly — student is visibly parked, not skipped).                                                                        |
  | `unanswered`   | Question closes permanently. Writes `{status:'submitted', unresponded:'expired'}`.                                                                                                                   |

- **`timeLimit` is forced to 0 on recording questions** (`:3088-3105`,
  sub-decision 3) and stays **visible, disabled, with a hint stating why** —
  the house idiom at `components/common/library/AssignmentSettingsToggleGroup.tsx:283-293`
  (`disabled` + `hint` swap on `ToggleRow`), confirmed by RR-10 finding 3
  (`:2683-2690`). Do NOT hide the control. Speed bonus is unavailable by
  design on recording questions.
- **Recording lives in a new `recording` config block, separate from
  `timeLimit`.** Do not reuse `timeLimit` as the recording limit.
- **Hard stop at the stated limit, wrap-up warning before it, no grace
  tail** (`:3130-3146`, sub-decision 5). Not teacher-configurable. State the
  honest number; put the "wrap it up" signal inside the stretch before the
  limit, never past it.
- **No pause.** RR-A2 sub-decision 7 (`:3400-3414`) confirmed
  `MediaRecorder.pause()`/`.resume()` are native and continue into the same
  blob — there's no stitching cost — but pause is rejected anyway on
  assessment-validity grounds: "a 60-second limit a student can pause is not
  a 60-second limit." Once armed, the clock runs to commit, discard, or hard
  stop. `hooks/useScreenRecord.ts` is the only shipped recorder and it never
  calls `.pause()`/`.resume()` either — follow that precedent, don't add it.
- **Defaults: prep 30s, limit 60s. Maximum 300s for audio** (`:3184-3199`,
  sub-decision 8). (Video's 120s max and whiteboard's 180s/600s do not apply
  here — do not build UI for them.)
- **Countdown/progress must be driven by a client-side timer
  (`performance.now()`/`Date.now()`), never by the media element** — Chrome-
  recorded webm reports `Infinity` duration (`:2924-2928`, RR-A4 finding).
- **Nothing is written anywhere until the student commits** (`:3167-3182`,
  sub-decision 7). Bytes stay in memory (a JS `Blob`) from `armed` through
  `recording` through review. A crash loses the take; there is no
  autosave/draft analog for recordings. This is a hard constraint, not a
  nice-to-have — RR-A2 sub-decision 1 (`:3288-3312`) makes the discard the
  **only refusal mechanism** a student has, and it only works if nothing
  ever reaches the server before commit.

**Record → review → commit-or-discard (RR-A2, `docs/rich-response-wayfinder.md:3228-3486`):**

- Sub-decision 2 (`:3313-3332`): **discards are never counted and never
  written.** No Firestore document, no counter, no field anywhere records
  that a student declined to record. This is load-bearing for the refusal
  mechanism (sub-decision 1, `:3288-3312`) — do not add a discard counter
  "for analytics" or similar.
- Sub-decision 1 (`:3288-3312`): **there is no decline/refusal exit from a
  required question.** RR-08's submit block (brief 3.2/3.5 territory) binds
  a student who can record but chooses not to. This brief's job is only the
  capture UI; do not build a "I refuse" button that marks the question done.
  The discard IS the refusal — it just doesn't unblock Submit.
- Pre-commit review is free and local: "Record → review → commit or
  discard, at no cost" (`:3446-3450`). The student plays back the local
  blob before deciding. Reviewing does not count as a take, does not upload
  anything, and does not touch Firestore.
- No streaming during capture (sub-decision 7's constraint,
  `:3172-3177`) — do not chunk bytes to Storage/Firestore while recording is
  in progress, even for crash-recovery purposes. That would degrade the
  discard from a guarantee into a delete request.

**Tennessen notice (RR-04, `docs/rich-response-wayfinder.md:1437-1468`, sub-decision 5):**

- Renders **once per assignment, before the first recording** — not once per
  student per year, not always-visible static text. Must carry an explicit
  acknowledgment (a button the student presses), because absence of
  acknowledgment defeats the purpose (notice must be provable).
- **Four required elements** (Minn. Stat. § 13.04 subd. 2): purpose, whether
  the student may refuse, consequences of refusing, who else may receive
  the recording.
- **Required copy, not optional framing** (RR-A2 injection, `:1535`):
  - _May you refuse_ → **yes**, the discard remains "stop, don't keep
    this."
  - _What happens if you do_ → **the question stays incomplete and the
    assignment cannot be submitted.**
    Both sentences must appear. Omitting the second makes the "you may
    refuse" element false per § 13.04 subd. 2(c).
- A **persistent "why we're asking" link** stays on the recorder itself
  after the interstitial closes (not just on the one-time notice).
- **No always-on camera/mic preview before the interstitial is
  acknowledged.** This is audio-only, so there's no camera preview to worry
  about, but the mic must not be probed/activated until after
  acknowledgment either (no "test your mic" affordance pre-notice).
- The RR-05 clause about a teacher being able to send the recording to
  Gemini (`:1543`) is **not applicable here** — AI transcription is not
  planned (per IMPLEMENTATION.md standing decisions). Do not add that
  sentence to the notice copy.

**Told-and-moves-on when capture is unavailable (RR-07, `docs/rich-response-wayfinder.md:1954-2133`, resolution):**

- **There is no alternate/text format.** If the mic is unavailable
  (permission denied, device policy, dead hardware — RR-A4 finding 5), the
  student is **told plainly** and the slot is marked `capture-unavailable`
  and the student **moves on immediately** (resolution item 1, table at
  `:1971-1976`, and item 3 `:1996-2010`). Do not build a wait-for-teacher
  gate, a live-monitor hold, or a text-fallback textarea.
- Detector is **automatic capability failure**, not a student-raised flag
  (item 7, `:2043-2071`). Attempt to acquire the mic (via
  `getUserMedia`); on failure (any `NotAllowedError`, `NotFoundError`,
  or a track that reports muted/ended immediately), treat as unavailable.
  Do not ask the student to self-report "my mic doesn't work."
- The wording constraint that matters for a UI string you may need
  ("mic didn't work, this goes to your teacher"): **must not use the word
  "skip"** — it reads as the student getting out of the question rather
  than the question landing on the teacher's desk. State plainly that the
  question goes to the teacher ungraded and they'll be asked what to do
  with it (excuse / blank / offline substitute — those three outcomes are
  brief 3.4's grading UI, not this brief's, but the student-facing sentence
  must not promise a text alternative or imply the teacher can prevent this).
- A `capture-unavailable` slot must **not block Submit** (resolution item
  8, `:2073-2077`) — same carve-out RR-08 grants the addendum case: the
  block only binds students for whom the requirement was ever satisfiable.

## 4. Step-by-step implementation notes

1. **Add the `recording` config type to `types.ts`**, adjacent to
   `QuizQuestion` (near line 3201, after `stimulusIds`):
   ```ts
   export type RecordingPrepExpiry =
     | 'auto-start'
     | 'auto-advance'
     | 'armed'
     | 'unanswered';
   export interface RecordingConfig {
     prepSeconds: number; // default 30
     limitSeconds: number; // default 60, max 300 for audio
     prepExpiry: RecordingPrepExpiry;
   }
   ```
   Add `recording?: RecordingConfig` to `QuizQuestion` and to
   `QuizPublicQuestion` (the requiredness/limit values must be visible to
   the student client without a Drive fetch — RR-08 sub-decision 5 depends
   on this).
2. **Add `unresponded?: UnrespondedReason` to `QuizResponseAnswer`** (if not
   already added by whichever ticket implements RR-08's core model —
   coordinate with brief 3.2, which shares this field). Vocabulary:
   `'passed' | 'expired' | 'abandoned' | 'capture-unavailable'` (RR-08
   `:2470-2473` — illustrative but this is the set both closed tickets
   settled on; do not add `'declined'`, RR-A2 explicitly rejected it).
3. **Build `hooks/useAudioRecording.ts`**, a new hook modeled on
   `useScreenRecord.ts`'s lifecycle but for `getUserMedia({audio: true})`:
   - States: `idle → requesting-permission → armed → recording →
reviewing → committed | discarded`.
   - `armed` starts the prep countdown (client timer, `performance.now()`).
   - Prep expiry dispatches on the question's `recording.prepExpiry`:
     `auto-start` transitions straight to `recording`; `auto-advance` and
     `unanswered` bubble an event up to the question renderer to write the
     appropriate `unresponded` entry and advance/close; `armed` just stops
     the countdown display and leaves the button live.
   - `recording` runs a `MediaRecorder` against the acquired stream, with
     a client-side countdown to `limitSeconds`. Show a wrap-up warning in
     the final ~10% of the limit (no grace tail — hard stop at exactly
     `limitSeconds`).
   - On hard stop or manual stop, transition to `reviewing` with the local
     `Blob` — do not touch Firestore/Storage yet.
   - `reviewing` offers playback (local `URL.createObjectURL(blob)`),
     commit, and discard. Discard returns to `armed` (or re-triggers
     acquisition) with the blob dropped and **zero writes**. Commit hands
     the blob + duration up to the caller (brief 3.2 turns this into an
     artifact + upload).
   - Mic acquisition failure (any error, or a track whose `readyState`
     never becomes `'live'`) surfaces a distinct `capture-unavailable`
     state rather than a generic error — this is what the question
     renderer uses to write `unresponded: 'capture-unavailable'` and move
     on (RR-07 resolution item 1/3).
4. **Gate the whole capture flow behind `canAccessQuizMediaResponse`** (see
   Owner notes above / GLOSSARY.md) before it renders anything — the
   Tennessen notice, the record button, and the mic-permission prompt must
   all be unreachable when the fail-closed check denies access. Hide the
   entire recording-mode branch (fall back to whatever the question's other
   response modes render, or nothing if audio is the only mode), do not
   disable-and-explain.
5. **Build the Tennessen interstitial component** (e.g.
   `components/quiz/RecordingConsentNotice.tsx`), shown once per assignment
   before the first recording UI ever mounts. Persist "acknowledged" in
   the response doc (a boolean or timestamp field — coordinate the exact
   field name/shape with whoever lands RR-02's response-model changes, but
   this brief should introduce it if it doesn't exist, e.g.
   `QuizResponse.recordingNoticeAckedAt?: number`). Copy must include the
   four required elements and the two required refusal/consequence
   sentences verbatim in substance (exact wording is this brief's to
   write, but it must state: purpose, "you may refuse — press stop and
   discard," "the question stays incomplete and the assignment can't be
   submitted," and who receives the recording — per RR-04 sub-decision 1,
   the teacher's Drive under the student's real name; do not mention AI/
   Gemini since transcription isn't planned).
6. **Wire the capture flow into `QuizStudentApp.tsx`'s question renderer**
   (near the type-switch at `:2609-2938`): when the question's
   response-mode set includes `'audio'`, render the recording UI in place
   of (or alongside, if modes include text too) the existing inputs. On
   commit, call an extended `onAnswer`/`onCommitRecording` that produces a
   `QuizResponseAnswer` with `answer: ''` and the artifact metadata (brief
   3.2 territory for the actual `artifacts[]` write — this brief should at
   minimum stub the call site and leave a clear TODO/interface boundary).
7. **Light state.** Prep/armed/recording/review are pure client state; do
   not write draft entries to Firestore during the flow. Only the terminal
   transitions (`auto-advance`/`unanswered`/`capture-unavailable` at
   expiry, or a commit) touch `submitAnswer`.
8. **Container-query scaling.** The recording UI (countdown ring, record
   button, waveform/level meter, review player) is student-app front-face
   content — per CLAUDE.md's Content Scaling section, size every element
   with `cqmin`-based `style` props, never hardcoded Tailwind size
   classes. The student app is light-theme; follow CLAUDE.md's Design
   Context guidance (calm, glass-adjacent, no placeholder-looking spinner-
   and-microphone-emoji UI). Use `ScaledEmptyState`-equivalent restraint:
   the recorder should read as a considered, premium control, not a raw
   `<button>MediaRecorder.start()</button>`.
9. **Wrap-up warning copy** must state the honest number the student was
   told — do not silently extend the limit and don't invent a second
   "real" number.

## 5. Backward-compatibility constraints

- `recording` is optional on `QuizQuestion`/`QuizPublicQuestion`. Every
  existing quiz has no `recording` block and must render exactly as today
  — no code path may assume its presence.
- `unresponded` is optional on `QuizResponseAnswer`. Absence still means
  "the student hasn't got there yet" (RR-08 sub-decision 1) for every
  pre-existing response.
- No Firestore rules changes in this brief. If the capture/commit flow
  needs a rules change (e.g. to permit writing `unresponded` or a new
  response field), describe it under a "Protected-file change needed"
  note in your PR rather than editing `firestore.rules` directly.
- No Storage rules or index changes. Artifact upload/Storage paths are
  brief 3.2/3.3's concern, not this brief's — this brief should stop at
  "I have a committed local Blob and its duration," and hand off cleanly.
- Existing MC/FIB/Matching/Ordering/short/essay questions (no response-mode
  set, or a set with no `'audio'`) must be byte-for-byte unaffected by
  this change — verify by running the existing student-app test suite (see
  §6) unmodified and confirming it stays green.

      capture flow (Tennessen notice, record button, mic prompt) — hidden,
      not disabled-and-explained, when the check denies access.

      refusal/consequence sentences; acknowledgment is persisted and
      gates arming.

      works for all four `prepExpiry` values, driven entirely by a
      client-side timer (never the media element's duration).
- [ ] No grace tail; the stated limit is the real limit.
- [ ] No pause/resume anywhere in the recorder.
- [ ] Nothing is written to Firestore/Storage until commit; discard is
      silent and leaves zero trace.

      `capture-unavailable`, and lets them move on — no wait state, no
      text-fallback UI, does not block Submit.
- [ ] `timeLimit` is forced to 0 (and rendered disabled-with-hint, not
      hidden) wherever the authoring UI touches a recording question —
      cross-check against brief 3.5.

      (verified by test, not just by inspection).
