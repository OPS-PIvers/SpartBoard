# Brief 1.2 — Four-consumer `takeIndex` ordering fix

Source of truth: `docs/rich-response-wayfinder.md`. Map tickets: RR-A2 (closed
2026-08-06, sub-decision 5), RR-08 (closed 2026-08-06, referenced for the
companion rule). Implementation order: `docs/rich-response/IMPLEMENTATION.md`,
Phase 1 fix 2.

This is a standalone implementation brief. You have no access to the
conversation that produced it — everything you need is below or in the two
docs cited above.

## 1. Goal

Change four "credit only the first entry per `questionId`" scoring/stat
consumers from **first-occurrence-wins** to **highest-`takeIndex`-wins, ties
broken by earliest `answeredAt`** — but only once `takeIndex` actually exists
on `QuizResponseAnswer`/`VideoActivityAnswer`. Until that field exists, this
brief's job is to **make the four call sites `takeIndex`-ready** (accept and
prefer it when present, fall back to the current first-occurrence behavior
when it's absent) so the append-based takes feature (brief 3.2, RR-A2) can
land without a silent mis-grade window.

## 2. Decisions to honor

**RR-A2 sub-decision 5** (`docs/rich-response-wayfinder.md:3364-3386`):

- Takes append as sibling `answers[]` entries carrying an explicit
  `takeIndex: number`. Quiz's shipped model replaces; this picks Video
  Activity's append behavior for the recording feature specifically.
- **"Latest wins" is explicitly the WRONG fix.** The four consumers must
  become **"highest `takeIndex` wins, ties broken by earliest `answeredAt`."**
  The tie-break exists because a race-created duplicate (e.g. an `arrayUnion`
  race, or a Drive-sync double-write) carries the **same** `takeIndex` as the
  original — so first-wins-within-index preserves the original guard's
  behavior byte-for-byte for the bug it was written against (#1728, #1777),
  while a genuine retake (which carries a strictly higher `takeIndex`) wins
  cleanly. Flipping straight to "plain latest `answeredAt`" reopens both bugs.
- `takeIndex` is the **sort key**, not `answeredAt` — deliberately, so a
  race-created duplicate (same index) and a genuine retake (higher index)
  stay distinguishable (`:622`).
- The four named consumers: `quizScoreboard.ts:55-71`,
  `questionAccuracyStats.ts:1-35`, `useQuizAssignments.ts:2000-2035`,
  `useVideoActivityAssignments.ts:997,1028` (map's original line numbers —
  see §3 for current locations, which have drifted).
- **Ordering constraint, stated twice in the map** (RR-A2 `:3454`, RR-08
  `:3476`): this fix "lands with the append change or before it, never
  after." The window where `answers[]` holds two entries for one
  `questionId` and these consumers still credit the first one is a silent
  mis-grade — no error anywhere, no test failure, just a wrong number. Since
  brief 2.1 (this map's Phase 2 slice 1) does not itself add `takeIndex`
  (only `artifacts[]`/`artifactArchive`), and `takeIndex` is scheduled for
  brief 3.2 (RR-A2's takes slice), **this brief must ship before or
  alongside 3.2 — not after.**
- **`takeIndex` is defined on `QuizResponseAnswer`, not on the recording path
  specifically** (`:3455`). Whether Video Activity's `VideoActivityAnswer`
  ever gains a `takeIndex` field is genuinely unresolved by the map — see §8.

**RR-06's confirmation** (`docs/rich-response-wayfinder.md:1739-1740`):
scoring reads the highest `takeIndex`; three of the four consumers are named
again there as "must change in lockstep with the append... until they read
`takeIndex`, the scoreboard grades take 1 while the results view shows take
3 — silently, with no error anywhere."

## 4. Step-by-step implementation notes

1. **Confirm `takeIndex`'s landing state before writing any logic.** Check
   `types.ts` for `takeIndex` on `QuizResponseAnswer`. If brief 3.2 has
   already landed it, this brief consumes the field as-is. If not, add
   `takeIndex?: number` to `QuizResponseAnswer` in this brief (coordinate to
   avoid a duplicate/conflicting add from brief 3.2) — optional so every
   existing response document (which has none) is unaffected.
2. **Write one shared helper** rather than four independent
   implementations of the same tie-break, e.g. in
   `utils/quizScoreboard.ts` (or a new small shared util both quiz and VA
   utils can import — check whether `components/widgets/QuizWidget/utils/`
   and `components/widgets/VideoActivityWidget/components/` already share a
   utils module before creating a new one):
   ```ts
   /**
    * Reduce a list of answers (possibly several entries per questionId) to
    * one representative answer per questionId: the highest `takeIndex`
    * wins; entries with equal (or absent) takeIndex are broken by earliest
    * `answeredAt`. Absent `takeIndex` is treated as 0 for every entry, which
    * exactly reproduces today's first-occurrence-by-answeredAt behavior on
    * documents written before takes existed.
    */
   function selectRepresentativeAnswers<
     T extends { questionId: string; answeredAt?: number; takeIndex?: number },
   >(answers: T[]): Map<string, T> {
     const sorted = [...answers].sort((a, b) => {
       const ai = a.takeIndex ?? 0;
       const bi = b.takeIndex ?? 0;
       if (ai !== bi) return bi - ai; // higher takeIndex first
       return (a.answeredAt ?? 0) - (b.answeredAt ?? 0); // then earliest answeredAt
     });
     const byQuestion = new Map<string, T>();
     for (const a of sorted) {
       if (!byQuestion.has(a.questionId)) byQuestion.set(a.questionId, a);
     }
     return byQuestion;
   }
   ```
   Note the sort direction: because higher `takeIndex` should win, and
   equal-`takeIndex` ties should go to the earliest `answeredAt`, a single
   comparator that sorts descending-by-takeIndex-then-ascending-by-answeredAt
   and takes "first seen per key" reproduces the intended precedence without
   two passes.
3. **`quizScoreboard.ts`:**
   - `getEarnedPoints` (lines 42-112): replace the manual
     `sortedAnswers`/`seenQuestionIds` loop (lines 53-71) with the shared
     helper, then iterate `byQuestion.values()` for scoring (the rest of the
     function body, lines 72-109, is unchanged — it just needs the
     dedup input).
   - `isResponseAwaitingGrade` (lines 234-257): same replacement for its
     private `sortedAnswers`/`seen` loop (lines 241-249). Its own comment
     (line 239-240) already says it must match `getEarnedPoints`'s dedup
     exactly — using the same shared helper is what makes that a guarantee
     rather than a convention.
4. **`questionAccuracyStats.ts`:** both functions currently take "first in
   array order," not "first by `answeredAt`." Route both through the shared
   helper (which sorts internally) rather than patching in a local sort —
   this closes the array-order gap noted in §3 as a side effect, and is the
   correct fix regardless (the file's own header comment says it must track
   `computeVideoActivityScorePct`'s semantics, and that function — see §8 —
   already sorts).
   - `computeQuestionAccuracy` (lines 22-38): replace the
     `r.answers.find(...)` per-response, per-question lookup with one
     `selectRepresentativeAnswers(r.answers)` call per response (hoist it
     out of the per-question inner logic if this function is called once per
     question across many responses — check the call site to avoid
     recomputing the map once per question; if needed, take a
     pre-computed `Map<questionId, answer>` as a parameter instead of
     `responses: ResponseLike[]` and have the caller build it once per
     response).
   - `countCorrectAnswers` (lines 40-59): replace the manual `firstAnswers`
     Map-building loop (lines 45-50) with the shared helper.
5. **`useQuizAssignments.ts` `publishAssignmentScores`** (lines 2140-2216):
   the `answers.map((a) => {...})` callback (line 2150) both grades every
   answer for its `isCorrect` flag (needed on every entry, unchanged) AND
   conditionally accumulates points via `scoredQuestionIds` (lines
   2172-2179). Precompute `selectRepresentativeAnswers(answers)` **before**
   the map, then change line 2172-2176's condition from "is this the first
   occurrence of this questionId" to "is this answer object reference-equal
   to (or `===` by `questionId` + `answeredAt` + `takeIndex`, if you can't
   rely on reference identity through the map) the representative answer for
   this questionId." Keep the per-entry `isCorrect` grading (line 2170)
   unconditional — every stored answer still gets a fresh `isCorrect`
   regardless of whether it's the scoring representative, matching current
   behavior (line 2180's `return { ...a, isCorrect: result.isCorrect }` runs
   for every entry, not just the winner).
6. **`useVideoActivityAssignments.ts` `publishAssignmentScores`** (lines
   995-1045): identical shape and identical fix as step 5 — precompute the
   representative map before the `answers.map(...)` callback (line 1008),
   gate the `pointsEarned`/`pointsMax` accumulation (lines 1020-1024) on
   representative-answer identity instead of first-occurrence.
7. **Do not touch `answeredQuestionIds` denominator loops** in either
   `useQuizAssignments.ts` (lines 2196-2203) or
   `useVideoActivityAssignments.ts` (around line 1040) — these are
   presence-only Sets (a question counts once toward the "unanswered"
   denominator regardless of how many entries it has), not sums, so
   first-vs-highest-takeIndex is not a distinction that affects them.

## 5. Backward-compatibility constraints

- `takeIndex` is optional. Every existing Firestore document (all of them,
  today) has no `takeIndex` on any answer entry. The shared helper in §4
  step 2 treats a missing `takeIndex` as `0` for every entry — meaning on
  every document written before this ships, the ordering degenerates to
  "all ties, broken by earliest `answeredAt`," which is **exactly today's
  first-occurrence-by-`answeredAt` behavior** in `quizScoreboard.ts`. For
  `questionAccuracyStats.ts`, `useQuizAssignments.ts`, and
  `useVideoActivityAssignments.ts` — which currently use raw array order,
  not `answeredAt` order — this is a **behavior change on legacy documents
  with duplicate entries** (a race-created duplicate). Confirm this is
  intended: it moves those three from "first written" to "first answered,"
  which is more correct (matches `quizScoreboard.ts`'s existing behavior)
  but is a real diff. Call this out explicitly in the PR description.
- No Firestore rules changes. `takeIndex` (if added here) needs no rule —
  same reasoning as `artifacts[]`/`unresponded` in brief 2.1/2.2: rules
  cannot validate array element shape or inspect a specific field's value
  across `answers[]` entries, so there's nothing to gate.
- No change to what gets written to Firestore in this brief — this is a
  **read-side** ordering fix only. The actual `takeIndex` writer is brief
  3.2's `submitAnswer`/retake-commit path.
