## 1. Goal

Add the per-question recording controls (prep, limit, expiry, take limit) to
the existing quiz-question editor, clamped to whatever ceiling the authored
response-mode set implies, plus a live, non-blocking advisory banner in the
editor that names storage exposure, shuffle no-ops, and required-addendum
walls as the teacher builds — without adding any new tab, pane, or shell.

## 2. Decisions to honor

**What's authorable and where it lives (RR-10, table at `docs/rich-response-wayfinder.md:2605-2613`):**

- The `recording` block: prep, limit, and the four-value expiry setting
  (`auto-start`/`auto-advance`/`armed`/`unanswered`) — from brief 3.1.
- `takeLimit`, defaulting to unlimited — from brief 3.2.
- The response-mode **set** (≥1 value) with an optional addendum the
  teacher may mark required — from RR-01 (assumed already shipped as a
  Phase-2 prerequisite; verify before starting, see §3).
- Stimulus attachment (format, replay policy, multi-select pointer) — RR-C3,
  **already shipped** in this codebase (`StimulusManagerPanel.tsx`,
  `QuestionStimulusSection` inside `QuizEditor.tsx`). Not this brief's to
  build; only relevant here because the live advisory (sub-decision 5, see
  below) must surface RR-C3's shuffle no-op alongside the recording-driven
  warnings.

**One `recording` block, clamped to the lowest ceiling in the authored mode set (RR-10 sub-decision 4, `docs/rich-response-wayfinder.md:2796-2815`):**

- `['audio','video']` means the student picks the mode at capture time
  (RR-A3 sub-decision 2). Audio's ceiling is 300s (RR-A1 sub-decision 8);
  video's is 120s. **This codebase does not build video capture** (deferred
  per IMPLEMENTATION.md), so in practice the only mode this brief ships is
  `'audio'` — but the **editor's authoring model must not assume
  audio-only**, because a question authored with `'video'` in its mode set
  (even though no video UI runs yet) still needs its `recording.limitSeconds`
  clamped correctly if/when video's ceiling matters. Concretely: **the
  limit's authorable maximum is the minimum ceiling across the modes
  present in the question's response-mode set**, using RR-A1's numbers
  (audio 300s, video 120s — whiteboard's 180s/600s do not apply, B track is
  deferred and out of scope).
- **This is one block, not one per mode** — one prep, one limit, one expiry
  value, shared across whichever modes the question authors. Do not build
  per-mode field groups.
- **Accepted cost, and it needs the disabled-with-hint idiom, not a silent
  clamp:** if a teacher adds `'video'` to a question already authored at
  audio's 300s ceiling, the limit re-caps to 120s. The field must stay
  visible, state the new ceiling, and name the mode that imposed it (e.g.
  "Capped at 120s — video's limit"). Follow the house idiom already shipped
  at `components/common/library/AssignmentSettingsToggleGroup.tsx:283-293`
  (`ToggleRow`'s `disabled` + `hint` swap for `shuffleQuestionsAvailable`) —
  do not silently mutate the number with no explanation.
- Since video capture isn't built, in practice this brief will only ever
  clamp against `'audio'`'s 300s ceiling — but write the clamp logic
  mode-generically (a small ceiling-per-mode lookup table) so it needs no
  rework when video ships.

**`timeLimit` stays visible, disabled, with a hint — never hidden (RR-10 finding 3, `docs/rich-response-wayfinder.md:2683-2690`):**

- This corrects a claim that circulated in the map's own inventory table
  (`:2608`) that `timeLimit` "hides" on a recording question. It does not
  hide — RR-A1 sub-decision 3 forces it to `0` (brief 3.1's job to enforce
  at runtime), and this brief's job is to render the editor's `timeLimit`
  field **visible and disabled**, with the hint text stating why (e.g.
  "Disabled — recording questions use their own timer instead of speed
  bonus"). Do not conditionally unmount the field.

**No new tab, no new pane, no new shell (RR-10 sub-decision 2, `docs/rich-response-wayfinder.md:2749-2777`, and derived note `:2887-2889`):**

- The session that produced RR-10 explicitly **rejected** a `Questions |
Stimuli | Settings` three-tab structure for the stimulus library, on the
  grounds that it makes the library "a first-class object the teacher has
  to visit" for something they only ever want as "this question needs that
  passage." **⚠️ The current codebase has exactly that rejected shape
  already built** — `QuizEditorModal.tsx:332` renders a `['questions',
'stimuli', 'settings']` three-tab segmented control, with a dedicated
  `StimulusManagerPanel` for the `'stimuli'` tab (`:356-357`). **Do not
  treat this as license to add a fourth `'recording'` tab.** This brief adds
  **zero new tabs**, full stop — the recording controls live inside the
  existing per-question detail pane (see §3/§4), and the advisory lives in
  the existing banner slot. See §9 for how to report this disagreement
  rather than silently resolving it.

**The live advisory (RR-10 sub-decision 5, `docs/rich-response-wayfinder.md:2816-2841`):**

- The context pane's banner slot — currently only ever a save error at
  `QuizEditor.tsx:157-162` (verify current lines; the map cites `:154-159`
  from an earlier snapshot) — gains an **advisory tone**, updating live as
  the teacher authors, alongside (not replacing) the existing error
  rendering.
- **Carries three classes of warning, all non-blocking:**
  1. A mode struck by the district's video gate (RR-A3 sub-decision 3) —
     this brief renders the copy; the actual gate-check plumbing may not
     exist yet since video capture is deferred. If the district-gate signal
     isn't available client-side, **skip this class rather than fabricating
     a check** — do not build a fake always-off gate just to satisfy the
     inventory. Note its absence in your PR description.
  2. RR-C3 sub-decision 5's component-aware shuffle collapsing to a no-op
     when stimulus pointers overlap (already-shipped stimulus code; this
     brief only needs to read whatever signal that logic already exposes,
     not reimplement shuffle grouping).
  3. **Required addenda a restricted-OU student can never satisfy** — this
     is the class this brief actually delivers end-to-end: a question
     whose addendum (or whose entire mode set) is `required` and offers no
     satisfiable path. Fires whenever a question authors a required
     recording addendum or a required-only recording primary mode.
- **This is the first warn-but-permit surface in the codebase** (RR-10
  finding 4, `:2691-2700` — every existing guardrail either hard-refuses an
  upload or blocks save via `QuizEditorModal.tsx`'s collect-errors-show-
  first pattern, map cites `:197-213`). Do not make this a blocking
  validation; do not fold it into the existing save-error path. It updates
  live, without requiring a save attempt.
- **RR-A3's pre-launch warning is NOT replaced by this advisory** — that
  warning (shown at session launch, naming affected questions when the
  district gate strikes a mode after authoring) stays exactly as it is; it
  catches degradation an editor-time check structurally cannot see (a gate
  flipped after authoring, or a PLC-imported quiz from a different
  district). This brief does not touch launch-time code at all.
- **Exact required wording for the required-addendum/device-blocked
  advisory (RR-07 resolution item 10, `docs/rich-response-wayfinder.md:2084-2098`,
  which RR-10 came to RR-07 to collect):**

  > _"If a student's device blocks the microphone, the question comes to
  > you ungraded — you choose whether it's excused, scored zero, or
  > answered another way."_

  Use this sentence (or a close paraphrase preserving its exact
  constraints) rather than inventing new copy. **Constraints, verbatim from
  the map:**
  - **Must not use the word "skip"** — reads as the student getting out of
    the question rather than it landing on the teacher's desk with a
    decision attached.
  - **Must not promise a text alternative** — there isn't one (RR-07
    resolution item 6, `:2030-2041`).
  - **Must not imply the teacher can prevent the wall** — they cannot; the
    device policy is upstream of the assignment.

**Storage appears as a neutral figure, not a warning (RR-10 sub-decision 6, `docs/rich-response-wayfinder.md:2843-2861`):**

- The advisory states what the quiz will do — **"records up to N slots per
  student"** (exact register: a fact, not a judgment; match the tone of the
  shipped behavior summary at `utils/quizBehavior.ts`'s
  `formatBehaviorSummary`, map cites `:65-81`).
- `N` = count of recording **slots** (RR-06 sub-decision 10's unit — cost
  scales with slots, not questions; nine MC + one video question is one
  slot). This brief computes `N` as the count of questions/addenda whose
  response-mode set includes a recording mode, **not** takes × questions
  (there is no bound to project against, `takeLimit` defaults unlimited —
  do not compute or display an estimated byte total).
- **Do not reopen the `takeLimit` unlimited default.** This was a
  deliberate choice (brief 3.2, RR-A2 sub-decision 4) and this brief must
  not add a threshold warning, a suggested cap, or any UI nudging the
  teacher toward a specific `takeLimit` value. State the fact, nothing
  more.
- This also answers RR-06's one open item ("does a count of hand-graded
  slots appear anywhere") — the same `N` figure serves both purposes (RR-10
  derived note, `:2881-2886`). Do not build a second counter for the
  grading side; the existing `Manual` badge at
  `components/widgets/QuizWidget/components/QuizResults.tsx` (map cites
  `:1850`) stays the grading-side home and needs no change from this
  brief.

**Every authored control gets a read-site test (RR-10 sub-decision 7, `docs/rich-response-wayfinder.md:2863-2877`):**

- This is the map's own standing rule, stated as a direct response to a
  real shipped bug: Video Activity's `shuffleAnswerOptions` toggle is
  persisted, summarized in the UI, and **never read at runtime**
  (`QuestionOverlay.tsx` shuffles unconditionally regardless of the flag —
  RR-10 finding 8, `:2718-2727`). **Every control this brief adds
  (`recording.prepSeconds`, `.limitSeconds`, `.prepExpiry`, `takeLimit`, the
  addendum-required flag if newly touched here) must have at least one test
  asserting a runtime code path actually consults it** — not merely that it
  round-trips through save/load. Cross-reference brief 3.1's and 3.2's test
  suites; this brief's test obligation is to confirm the _editor writes the
  field the runtime reads_, closing the loop end to end.

## 4. Step-by-step implementation notes

1. **Confirm prerequisites exist** (response-mode set on `QuizQuestion`,
   `recording?: RecordingConfig` from brief 3.1, `takeLimit` from brief
   3.2). Stop and flag if any are missing rather than authoring against a
   speculative shape.
2. **Build `RecordingConfigSection`** (e.g.
   `components/widgets/QuizWidget/components/RecordingConfigSection.tsx`),
   mounted inside `QuizEditor.tsx`'s per-question detail pane immediately
   after `QuestionStimulusSection` (before the rubric-builder conditional),
   rendered only when the question's response-mode set includes a
   recording mode (`'audio'` — `'video'`/`'whiteboard'` are deferred but
   the section should not crash if they appear in the set; just include
   them in the ceiling-clamp lookup).
   - Fields: prep seconds (number input, default 30), limit seconds
     (number input, default 60, hard-capped in the UI at the clamped
     ceiling per mode-set — see decision above), expiry (a 4-option
     control for `auto-start`/`auto-advance`/`armed`/`unanswered`, each
     with a one-line description matching the table in brief 3.1 §2), and
     take limit (a nullable number input — empty/blank means unlimited,
     matching the `attemptLimit` UI convention already shipped elsewhere
     in this editor's Settings tab via `QuizBehaviorSettingsPanel` — reuse
     that same nullable-number input pattern rather than inventing a new
     one).
   - All writes go through `updateQuestion(q.id, { recording: {...} })`.
   - The limit field applies the disabled/hint idiom when the authored
     value exceeds the newly-clamped ceiling (e.g. teacher had 300s
     authored, then adds `'video'` to the mode set): field becomes
     read-only at the new ceiling with hint text naming which mode caused
     it, per the decision above — do not silently rewrite the stored
     number without the teacher seeing why.
3. **Render `timeLimit` visible-and-disabled for recording questions.**
   Find wherever `timeLimit` is currently rendered in the per-question
   editor (grep `QuizEditor.tsx` for `timeLimit`) and apply the same
   `disabled` + `hint`-swap idiom, with hint copy along the lines of
   "Recording questions use their own prep/limit timer — speed bonus
   isn't available here." Do not conditionally unmount the input.
4. **Build the live advisory.** Add a small pure function (e.g.
   `utils/quizAuthoringAdvisory.ts`) that takes the current `questions:
QuizQuestion[]` (and whatever stimulus-overlap signal RR-C3's code
   already exposes) and returns a list of advisory strings:
   - One line per recording slot count: `"Records up to N slots per
student."` when `N > 0`, nothing when `N === 0`.
   - One line using RR-07's exact required wording (§2 above) whenever any
     question has a required recording mode or a required recording
     addendum.
   - One line when RR-C3's shuffle-overlap signal indicates a no-op (only
     if that signal is already exposed by shipped stimulus code — do not
     build new overlap-detection logic in this brief).
   - Skip the district-video-gate class entirely if no client-readable
     gate signal exists yet (see decision above).
     Render this list in `QuizEditor.tsx`'s banner slot, visually distinct
     from the existing red error styling (map calls this an "advisory tone"
     — use a neutral/informational treatment, e.g. slate or amber, not the
     `brand-red` classes used for `error`). It must update on every keystroke/
     toggle change (derive it inline from `questions` in the render body or
     via `useMemo`, per CLAUDE.md's "compute derived values inline" rule —
     do not stash it in `useEffect` + `useState`).
5. **Do not add a new tab.** Verify your diff touches zero lines in the
   `['questions','stimuli','settings']` array at `QuizEditorModal.tsx:332`
   and adds no new `editorTab` branch.
6. **Styling.** This is teacher-authoring UI (not student front-face), so
   CLAUDE.md's container-query scaling rules do not apply here — normal
   Tailwind classes are fine, matching the existing editor's visual
   language (slate/brand-blue palette already used throughout
   `QuizEditor.tsx`).

## 5. Backward-compatibility constraints

- Every new field (`recording.takeLimit`, the expiry value, etc.) is
  optional. A quiz with no `recording` block on any question must render
  identically to today — no advisory line, no new section rendered, no
  `timeLimit` disabling.
- The advisory function must return an empty list (rendering nothing) for
  every quiz that predates this feature.
- No Firestore rules or Storage rules changes. No index changes.
- `QuestionStimulusSection` and `StimulusManagerPanel` (already shipped)
  are not modified by this brief beyond, if strictly necessary, reading an
  already-exposed overlap signal for the advisory — do not refactor their
  internals.

## 9. Disagreement to report, not silently resolve

The map's RR-10 resolution (sub-decision 2, `docs/rich-response-wayfinder.md:2749-2777`)
explicitly **rejected** a `Questions | Stimuli | Settings` three-tab editor
shape in favor of "the picker is the library" — no third tab. **The current
codebase already has that rejected three-tab shape shipped**
(`QuizEditorModal.tsx:332`, `['questions', 'stimuli', 'settings']`, with a
dedicated `StimulusManagerPanel` component for the `'stimuli'` tab) —
apparently built by whoever implemented RR-C3 before, or independently of,
this map's RR-10 session. This brief does not resolve that disagreement
(reverting shipped UI is out of scope for an authoring-controls brief) — it
only holds the line that **this** brief adds no further new tabs, and flags
the existing contradiction in the PR description so a human can decide
whether to leave the three-tab shape as a superseding-in-practice decision
or file a follow-up to collapse it into RR-10's picker-only model.
