# Brief 2.1 — `ResponseArtifact[]` + `artifactArchive` on `QuizResponseAnswer`

Source of truth: `docs/rich-response-wayfinder.md`. Map tickets: RR-02 (closed
2026-08-05), RR-03 (closed 2026-08-05, sub-decision 3 amends RR-02), RR-01
(closed 2026-08-04, for the "capability not type" framing this schema
serializes). Implementation order: `docs/rich-response/IMPLEMENTATION.md`,
Phase 2 slice 1.

This is a standalone implementation brief. You have no access to the
conversation that produced it — everything you need is below or in the two
docs cited above.

## 1. Goal

Add a sibling `artifacts?: ResponseArtifact[]` field to `QuizResponseAnswer`
(never overloading `answer: string`), and a server-owned sibling
`artifactArchive` map on `QuizResponse` keyed by artifact id. This is pure
schema + type-level work — no capture UI, no upload, no archival callable,
no recording config. It exists so brief 3.1 (student capture flow) has
somewhere to write artifact metadata, and so brief 1.2/1.3/2.2's fixes have
a concrete field shape to code against.

## 2. Decisions to honor

**RR-02 sub-decision 1** (`docs/rich-response-wayfinder.md:442-470`) — the
core shape:

```ts
interface QuizResponseAnswer {
  questionId: string;
  answer: string; // unchanged meaning: the primary answer, for every shipped type
  artifacts?: ResponseArtifact[]; // new, optional
  // ... answeredAt, isCorrect, speedBonus, status unchanged
}
```

Chosen over three rejected alternatives — **do not reintroduce any of
them**: encoding a reference into `answer` (killed by RR-01: one question can
own two artifacts, a delimiter scheme encodes badly on top of four existing
ad-hoc delimiter formats), a discriminated union on `answer` (killed by
blast radius across ~16 copy-pasted type-branch sites, rules can't validate
a union shape, every legacy-doc read needs a runtime guard), and a
subcollection (killed because the doc-size risk that motivated it doesn't
exist — see the ⚠️ correction at `:432-438`: `QuizResponse` is one doc **per
student**, not per class, so even 20 questions × 2 artifacts × ~250 bytes is
~10 KB against a 1 MB ceiling).

**RR-02 sub-decision 2, AS AMENDED by RR-03 sub-decision 3** — read both
together, the amendment is not optional:

RR-02's original shape (`:472-497`) put four archival fields directly on
`ResponseArtifact`. **RR-03 sub-decision 3** (`docs/rich-response-wayfinder.md:772-789`)
moved them off:

> Immediate archival means a server write lands while the student is still
> answering, and Firestore cannot address array elements by field path —
> `answers[3].driveFileId` is not expressible — so a server write into
> `answers[]` racing `submitAnswer`'s wholesale array rewrite needs a
> transaction. The fix is the pattern this codebase already invented for
> exactly this problem: `grading` lives outside `answers[]` so teacher
> writes never touch the student payload. So `driveFileId`, `archiveStatus`,
> `archivedAt` and `archiveError` move off `ResponseArtifact` into a sibling
> `artifactArchive` map keyed by artifact id. Student owns `answers[]`;
> server owns `artifactArchive`; no transaction, no race, and the rules
> whitelist stays truthful. `storagePath` and `uploadState` stay on the
> artifact — those are student-written.

**The final, amended `ResponseArtifact` shape** (`:472-497`, with the
archival fields struck per the amendment above):

```ts
interface ResponseArtifact {
  id: string; // minted client-side at record-stop; never changes
  slot: 'primary' | 'addendum';
  kind: 'text' | 'audio' | 'video' | 'whiteboard';
  text?: string; // inline, `kind: 'text'` only
  storagePath?: string; // Firebase Storage; nulled after archival
  mimeType?: string;
  bytes?: number;
  durationMs?: number; // recorded client-side — Chrome webm reports Infinity
  uploadState: 'pending' | 'uploaded' | 'failed';
}
```

**`artifactArchive` shape** (assembled from RR-03's description, not spelled
out as a single code block in the map — build it explicitly here). **This is
GLOSSARY.md's canonical shape** — it is written to match what the archival
callable (brief 3.3) and the org-admin delete console (brief 4.1) actually
need, rather than a placeholder they'd have to diverge from:

```ts
export type ArtifactArchiveStatus =
  | 'syncing' // archival in progress
  | 'archived'
  | 'failed'
  | 'deleted' // brief 4.1's compliance delete
  | 'delete-failed'; // brief 4.1's dead-teacher-token failure mode

// On QuizResponse, sibling to `answers[]`. Server-written only (via the
// archival callable's Admin SDK), keyed by ResponseArtifact.id.
export interface ArtifactArchiveEntry {
  driveFileId?: string;
  archiveStatus: ArtifactArchiveStatus; // required — an entry only exists once a status is known
  archiveStartedAt?: number;
  archivedAt?: number;
  archiveError?: string;
  deletedAt?: number;
  deletedBy?: string;
  deleteAttemptedAt?: number;
}

artifactArchive?: Record<string, ArtifactArchiveEntry>;
```

Every reader of `archiveStatus` treats anything other than `'archived'`
(with `driveFileId` present) as "not currently playable." The `'deleted'`/
`'delete-failed'`/`deletedAt`/`deletedBy`/`deleteAttemptedAt` members exist
for brief 4.1 and are unused by every earlier brief — add them now anyway
so 4.1 doesn't have to widen a type this brief already shipped.

**Sub-decision 3 — `id` is the identity, not the path** (`:472-509`):

`storagePath` and (later) `driveFileId` are facts about _where the bytes
currently are_, which the archive step rewrites; `id` never changes.
Rejected: making the path the identity (archival changes it — the reference
would dangle or force the archive step to rewrite student-owned data; also a
failed upload would have no identity at all). Rejected: storing a resolved
`getDownloadURL()` (privacy — a Firebase download URL is an unguessable but
permanent bearer token to a child's voice recording sitting in a Firestore
doc; RR-04 established these files are per-se regulated personal
information; paths force an authenticated fetch, URLs don't).

**Sub-decision 3 (numbered differently in the map's own text — the "one
array, any kind" decision) — text is an artifact too** (`:511-527`):

An MC question's required written justification has nowhere else to go —
`answer` already holds the MC selection — so a text addendum is
`{ kind: 'text', text: '...' , slot: 'addendum' }` with no `storagePath`.
`slot` is **stored on the response, never derived from the question config
at read time** — a quiz can be re-synced mid-flight (`preSyncVersion`
exists for exactly this), so a stored response and its current question
definition can legitimately disagree, and anything the response's meaning
depends on must travel with the response. Rejected: a media-only array plus
a separate `addendumText` field (splits the addendum across two locations by
mode). Rejected: promoting the primary text into `artifacts[]` too (dual-writes
every autosave, converts an additive change into a migration).

**Sub-decision 4 — upload state is its own axis, written before bytes
finish** (`:529-556`):

`answer.status` (draft/submitted) keeps its exact current meaning — student
intent. Each artifact's `uploadState` is separate, because an upload is a
system process that can fail after the student is gone. **Metadata lands in
Firestore at record-stop with `uploadState: 'pending'`**, and is patched to
`'uploaded'` when the transfer completes — not written only on success. This
ordering is this brief's to implement the _shape_ for; the actual write
sequencing (record-stop write, then patch-on-complete) is brief 3.1/3.2/3.3
territory once capture exists. This brief just needs the type to support
both states cleanly, with `'pending'` as a valid, expected, non-error value.

**Sub-decision 5 — bulk payloads are always files, never inline** (`:558-574`):

A whiteboard stroke timeline (when it ships) is a `storagePath` artifact,
exactly like audio — never inlined. The response doc's size is bounded by
question count regardless of content. The **sole exception** is the `text`
field from the "one array, any kind" decision, already capped by the
existing `maxWords` on written-response config. This is also a privacy
argument, not just a size one: all student content in files means one
deletion path (RR-04's deletion story), not two.

**Sub-decision 6 — `artifacts[]` is untrusted data; a path-prefix convention
plus a reader-side check carries the integrity** (`:575-599`). This is a
**hard constraint on Storage/Firestore rules that this brief must respect
even though it does not write the rules itself**:

- Firestore rules **cannot iterate arrays** — `storagePath` is
  unvalidatable by security rules.
- The mitigation: Storage rules gate uploads by path
  (`.../{sessionId}/{studentUid}/...`, extending the activity-wall
  pattern), and the **teacher's results view must refuse to render any
  artifact whose path prefix doesn't match that response's `studentUid`**.
  One comparison at a single render site; forging a path yields a broken
  tile, not a misattributed recording. **This brief does not build the
  render-time check or the Storage rule** (no capture/render UI exists yet —
  that's brief 3.1/3.6), but the field shapes (`storagePath` as a plain
  string, not a resolved URL) must not preclude it later.

**Consequences this brief must NOT re-decide, only preserve room for:**

- **`answer` is now legitimately `''`.** (`:603`) A pure-audio response
  stores an empty `answer` and puts everything in `artifacts[]`. This
  brief's job is only to make the type support it — brief 2.2/3.x fix the
  "answered" inference sites.
- **The archive step writes into a sibling map, not into `answers[]`**
  (`:604`, resolved by the RR-03 amendment above) — already incorporated
  into the shape in this section.
- **The Storage path shape `.../{sessionId}/{studentUid}/...` is fixed**
  by sub-decision 6 for whoever builds Storage rules later (brief 3.3) —
  this brief just needs `storagePath: string`, no format validation at the
  type level.
- **A `'pending'` artifact needs an owner** for retry/orphan handling — out
  of scope here, belongs to brief 3.2/3.3 (RR-A6).
- **`ResponseArtifact` is deliberately shaped like `ActivityWallSubmission`**
  (`:608`, `types.ts:1675` — read it for the precedent, do not copy its
  exact fields since `ActivityWallSubmission` has its own archival fields
  inline that RR-03 explicitly chose NOT to replicate here).

**RR-08's later addition to `QuizResponseAnswer`** (`:613`, closed
2026-08-06) — **not this brief's job**, but the interface this brief edits
is about to gain a second sibling field from brief 2.2:
`unresponded?: UnrespondedReason`. **Coordinate ordering with brief 2.2** —
whichever of the two briefs lands first should add its own field only, and
the second should find the interface already has the other's field present
without conflict (both are independently optional siblings on the same
interface, so there's no structural collision — just a potential merge
conflict on the same few lines of `types.ts`).

**RR-05's provenance gap this schema will need to answer, but not yet**
(`:632-637`, closed 2026-08-06) — flagged here so this brief's `kind` field
doesn't get over-fitted: a slot may later hold both a student-authored
artifact and a Gemini-authored transcript, and nothing in the shape above
says which is which. **This brief does not add a provenance field** — AI
transcription is not planned (IMPLEMENTATION.md standing decision), so the
concrete need doesn't exist yet. Do not add a speculative field for it.

**RR-06's later use of `slot` as a grading key** (`:642`, closed
2026-08-07) — confirms `slot: 'primary' | 'addendum'` (this brief's field,
unchanged) is later promoted to a grading sub-key. No action needed here;
recorded so you don't second-guess keeping `slot` a plain two-value union.

**Clarification on `VideoActivityQuestion`'s `Omit<QuizQuestion, ...>`
relationship** — IMPLEMENTATION.md's own note on this slice warns:
"`VideoActivityQuestion` inherits `QuizQuestion` fields at compile time —
decide `Omit` vs inherit in the same PR that adds any field." **Verified:
this warning does not apply to this brief's changes.** `ResponseArtifact`
and `artifactArchive` are new fields on **`QuizResponseAnswer`** and
**`QuizResponse`** respectively — the _answer/response_ types, not the
_question_ type. `VideoActivityAnswer` (`types.ts:5067-5074`) is a fully
independent interface that does **not** derive from `QuizResponseAnswer` —
confirmed by reading both interfaces; `VideoActivityAnswer` has its own
`questionId`/`answer`/`isCorrect`/`answeredAt` fields with no relationship
to this one. So adding `artifacts`/`artifactArchive` here has **zero blast
radius on Video Activity's types.** The `Omit<QuizQuestion, ...>` warning is
real and applies to `VideoActivityQuestion` (`types.ts:4755-4758`, which
does `Omit<QuizQuestion, 'type' | 'matchingDistractors' | 'stimulusIds'>`),
but only matters for a future brief that adds fields to **`QuizQuestion`**
itself (e.g. the `recording` config block in brief 3.1, or a primary
response-mode-set field from RR-01 if it hasn't landed by then) — not for
this one.

## 4. Step-by-step implementation notes

1. **Add `ResponseArtifact` and its supporting types to `types.ts`**, near
   `QuizResponseAnswer` (around line 3680):

   ```ts
   export type ArtifactSlot = 'primary' | 'addendum';
   export type ArtifactKind = 'text' | 'audio' | 'video' | 'whiteboard';
   export type ArtifactUploadState = 'pending' | 'uploaded' | 'failed';

   export interface ResponseArtifact {
     /** Minted client-side at record-stop; never changes. */
     id: string;
     slot: ArtifactSlot;
     kind: ArtifactKind;
     /** Inline text — `kind: 'text'` only. Nothing else is ever inlined. */
     text?: string;
     /** Firebase Storage path; nulled/cleared after archival to Drive. */
     storagePath?: string;
     mimeType?: string;
     bytes?: number;
     /** Client-recorded — Chrome webm reports Infinity on the media element. */
     durationMs?: number;
     uploadState: ArtifactUploadState;
   }
   ```

2. **Add `artifacts?: ResponseArtifact[]` to `QuizResponseAnswer`**
   (`types.ts:3680-3701`), with a doc comment explaining the sibling-not-overload
   rationale in one line (per CLAUDE.md's comment style — one line max, no
   multi-paragraph blocks):
   ```ts
   export interface QuizResponseAnswer {
     questionId: string;
     answer: string;
     answeredAt: number;
     isCorrect?: boolean;
     speedBonus?: number;
     status?: 'draft' | 'submitted';
     /** Media/text sub-responses (recording addenda, pure-audio answers). Sibling to `answer`, never overloads it. */
     artifacts?: ResponseArtifact[];
   }
   ```
3. **Add the archive entry type and `artifactArchive` to `QuizResponse`**,
   near wherever `QuizResponse.answers: QuizResponseAnswer[]` is declared —
   use the exact shape from §2 above (GLOSSARY.md canonical):
   ```ts
   export type ArtifactArchiveStatus =
     | 'syncing'
     | 'archived'
     | 'failed'
     | 'deleted'
     | 'delete-failed';
   export interface ArtifactArchiveEntry {
     driveFileId?: string;
     archiveStatus: ArtifactArchiveStatus;
     archiveStartedAt?: number;
     archivedAt?: number;
     archiveError?: string;
     deletedAt?: number;
     deletedBy?: string;
     deleteAttemptedAt?: number;
   }
   ```
   Add `/** Server-written only, keyed by ResponseArtifact.id — never written by the student client. */ artifactArchive?: Record<string, ArtifactArchiveEntry>;`
   as a sibling to `answers` on `QuizResponse`, in the same style as
   `grading` (an existing sibling map already on this interface — locate it
   and place `artifactArchive` near it for discoverability).
4. **Do not touch `firestore.rules`.** Confirm the student write whitelist
   (`:3360`) is unaffected — `artifacts` lives inside `answers[]` (already
   whitelisted as a whole array, and rules already can't validate element
   shape), and `artifactArchive` is server-only and must stay off the
   whitelist entirely.
5. **Verify the `submitAnswer` spread** (`useQuizSession.ts:2505-2520`, see

6. **Do not build**: capture UI, upload logic, the archival callable, the
   Storage path/rules, the render-time path-prefix check, or any consumer
   of `artifacts`/`artifactArchive` beyond the type definitions and the
   spread-preservation test. This is scaffolding only.

## 5. Backward-compatibility constraints

- Both new fields (`artifacts` on `QuizResponseAnswer`, `artifactArchive` on
  `QuizResponse`) are optional. Every existing Firestore document (all of
  them, today) has neither field — every reader must treat their absence as
  "no artifacts for this answer" / "nothing archived," which is trivially
  true since nothing writes them yet.
- No Firestore rules changes (§3, §4 step 4).
- No Storage rules changes — no upload path exists yet to gate.
- No index changes — these are not queried fields.
- Adding `artifacts`/`artifactArchive` to the TypeScript interfaces must not
  break any existing consumer that does an exhaustive object-shape check
  (e.g. a strict equality assertion in a test) — grep for any test that
  constructs a `QuizResponseAnswer` or `QuizResponse` literal and asserts on
  its exact key set (`Object.keys(...).toEqual([...])` or similar) before
  landing this change; none are expected to exist (optional fields don't
  appear in `Object.keys` when unset), but verify rather than assume.
