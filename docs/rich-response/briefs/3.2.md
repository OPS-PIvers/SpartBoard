# Brief 3.2 — Takes (append as siblings, takeIndex, takeLimit)

Source of truth: `docs/rich-response-wayfinder.md`. Map tickets: RR-A2
(closed 2026-08-06), RR-08 (closed 2026-08-06). Implementation order:
`docs/rich-response/IMPLEMENTATION.md`, Phase 3 slice 2 (builds directly on
Phase 1 hygiene fixes and Phase 2 foundations, and on brief 3.1's capture
flow).

This is a standalone implementation brief. You have no access to the
conversation that produced it — everything you need is below or in the two
docs cited above.

## 1. Goal

Make a committed recording append as a new sibling artifact carrying an
explicit `takeIndex`, rather than replacing the prior take, with an
authorable `takeLimit` (default unlimited) enforced server-side. Fix the
four shipped consumers that currently credit the chronologically-first
answer per question so they instead credit the highest `takeIndex` (ties by
earliest `answeredAt`), and land the fix in the same change as — or before —
the append behavior ships, never after.

## 2. Decisions to honor

**Takes append; `takeIndex` is explicit (RR-A2 sub-decision 5, `docs/rich-response-wayfinder.md:3364-3385`):**

- Quiz's shipped model **replaces**; this ticket makes recordings **append**,
  matching Video Activity's model. Each committed take is a new sibling
  artifact entry — do not delete or overwrite the prior take's artifact.
- **Four consumers must change in lockstep** — this is scheduled work that
  must land **with the append change or before it, never after**:
  - `utils/quizScoreboard.ts` (map cites `:55-71`; verify current lines —
    the map's own line numbers predate this session and may have drifted)
  - `utils/questionAccuracyStats.ts` (map cites `:1-35`)
  - `hooks/useQuizAssignments.ts` (map cites `:2000-2035`)
  - `hooks/useVideoActivityAssignments.ts` (map cites `:997,1028`)
- **The fix is "highest `takeIndex` wins, ties broken by earliest
  `answeredAt`"** — NOT plain "latest `answeredAt`." The tie-break matters:
  a race-created duplicate (e.g. from `arrayUnion` races or Drive-sync
  double-writes, cited bugs **#1728 and #1777**) carries the **same**
  `takeIndex`, so first-wins-within-index preserves the original guards'
  behavior for the case they were written against, while a genuine retake
  (higher index) wins. Flipping to plain "latest `answeredAt`" reopens both
  bugs. Read each consumer's existing comment/guard before touching it —
  they cite real shipped-bug numbers, not defensive boilerplate.
- Superseded takes are **kept, not deleted** (sub-decision 6, `:3387-3398`)
  — there is no cleanup problem to solve. Every committed take stays
  visible.
- Applies to `QuizResponseAnswer` generically (`takeIndex` is not
  recording-specific), so a future whiteboard mode inherits it for free —
  but that's out of scope here (B track deferred).

**`takeLimit` (RR-A2 sub-decision 3–4, `docs/rich-response-wayfinder.md:3333-3363`):**

- **`takeLimit: number | null`** lives in RR-A1's `recording` block (added
  in brief 3.1 — coordinate the exact field location; it belongs alongside
  `prepSeconds`/`limitSeconds`/`prepExpiry`). `null` means unlimited.
  Mirrors the shape and convention of the shipped
  `QuizBehaviorSettings.attemptLimit` (`types.ts:3184-3188` per the map;
  verify current line — see §3).
- **It counts takes, not re-takes.** `takeLimit: 1` means one take and no
  re-records — analogous to `attemptLimit` counting attempts, not
  re-attempts. Do not name the field or its semantics around "retakes";
  an off-by-one is the predictable bug if you do.
- **Default is unlimited** (`null`) — chosen deliberately by Paul against
  the recommendation of 3, to match the shipped norm that self-paced
  quizzes already allow unlimited uncounted re-submission
  (`components/quiz/QuizStudentApp.tsx`, comment near the resubmission gate
  calls revisits intentional — map cites `:2017`). Do not change this
  default; a teacher opting into a restrictive limit must be a deliberate
  authored act (this is also what brief 3.5's advisory copy communicates,
  not a code-level guardrail).
- **Enforced server-side in the archival callable, not in Firestore
  rules** (sub-decision 9, `:3430-3444`). Rules cannot do this:
  `hasAll(resource.data.answers)` requires prior array elements to survive
  byte-identical, which quiz's replace-then-promote-draft pattern already
  violates on the written-response path, and rules have **no array
  filtering** so a per-question take count is not rules-expressible under
  any model. This brief's job is the client-side plumbing (take counting,
  UI budget display, the append write); the actual server-side enforcement
  callable is **brief 3.3's** (the archival callable). This brief must,
  however, **not** implement a client-side-only enforcement and call it
  done — the client-side count is a UX aid, and the brief must leave a
  clear seam (e.g. a documented expected callable contract) for 3.3 to plug
  the authoritative check into.
- Discards are **never** counted toward `takeLimit` (sub-decision 2,
  already built in brief 3.1 — this brief must not regress it by e.g.
  counting a discard as consuming budget).

**Completeness predicate is unaffected by takes (RR-A2 sub-decision consequence, `docs/rich-response-wayfinder.md:3491`):**

- A question is complete iff every required slot is filled (RR-08
  sub-decision 7, `docs/rich-response-wayfinder.md:2364-2389`), and **any
  committed take fills its slot** — one take and six takes are identical to
  the predicate, to the student's binary progress count, and to the
  teacher's three-state view. Retakes change what's _in_ a slot, never
  whether it's filled. Do not add take-count-dependent logic to the
  completeness predicate.

**Every committed take is playable in the teacher's results view; no export column (RR-A2 sub-decision 8, `docs/rich-response-wayfinder.md:3415-3429`):**

- Deliberate split: takes need _a_ reader (the `history` subcollection
  precedent is write-only with no reader anywhere — don't repeat that), but
  the exported results sheet's only per-student integrity column is
  `Warnings` (`utils/assignmentExportShared.ts`, map cites `:125-140`), and
  **column adjacency is meaning** — a take count beside `tabSwitchWarnings`
  reads as an integrity signal it isn't. **This brief is not the results
  view** (that's 3.6) — but any code this brief adds to the export path
  must NOT add a take-count column. If your work touches
  `assignmentExportShared.ts` at all (e.g. because the "unanswered" cell
  fix below lives there), be surgical and do not introduce a takes column
  as a drive-by addition.

**The Sheets-export landmine this ticket must not trip (RR-06 finding, injected into RR-08, `docs/rich-response-wayfinder.md:2504`):**

- RR-08 sub-decision 1 (every passed-over question writes an entry) breaks
  `utils/assignmentExportShared.ts`'s "unanswered" cell logic — it currently
  emits `''` **only when no answer entry exists** for a question
  (`:170-178` per the map). Once every question writes an entry (brief 3.1's
  `unresponded` writes), the lookup starts hitting and the cell becomes
  `'0'`, which `quizDriveService.ts` documents as **"answered, incorrect"**
  (map cites `:817-821`). **This must land with the takeIndex/append change
  or before it, never after** — same rule as the four-consumer fix, and the
  map calls out this is "Phase 1 fix 3" territory
  (`docs/rich-response/IMPLEMENTATION.md`, Phase 1 item 3: "Absent-means-
  unanswered, four sites"). **Check whether Phase 1 has already landed**
  (grep for the four sites listed there:
  `assignmentExportShared.ts:170-178`, `quizDriveService.readPlcSheet`,
  `plcContributions.ts:99-114`, `quizDriveService.ts:718-741`) before doing
  any work here — if it's already fixed, this brief only needs to verify it
  covers the `unresponded`/`takeIndex` cases; if it's not fixed, this brief
  must implement it as a prerequisite, since shipping takes without it
  silently corrupts every teacher's exported gradebook.

## 4. Step-by-step implementation notes

1. **Add `takeIndex?: number` to `QuizResponseAnswer`** in `types.ts`, next
   to `unresponded` (brief 3.1). Document it as "present only on artifact-
   bearing (recording) answers; absent on text/MC-style answers, where a
   `questionId` is unique in `answers[]`."
2. **Add `takeLimit: number | null` to the `RecordingConfig` type** added
   in brief 3.1 (or add it here if 3.1 hasn't landed the field yet —
   coordinate). Default `null` (unlimited) wherever a `RecordingConfig` is
   constructed without explicit authoring input.
3. **Build the append-commit path.** In `useQuizSession.ts`, add a function
   parallel to `submitAnswer` (e.g. `commitRecordingTake(questionId,
artifact metadata, opts)`) that:
   - Reads `existingAnswers` for the question's prior takes (filter by
     `questionId`, look at max `takeIndex` present, default 0 if none).
   - Computes `nextTakeIndex = maxExisting + 1`.
   - **Client-side pre-check** against `recording.takeLimit` (from the
     question's config) purely for UX — disable/hide the "record again"
     affordance once the limit is reached. This is NOT the authoritative
     enforcement (that's 3.3's callable); label it clearly as advisory in
     a code comment so nobody mistakes it for the real gate.
   - Appends (does not filter-replace) the new `QuizResponseAnswer` entry
     with `takeIndex: nextTakeIndex`, `status: 'submitted'` (a committed
     take is always final — there is no draft state for a recording,
     brief 3.1 established review happens pre-commit from the local blob).
   - Goes through the same spread-safe write pattern `submitAnswer`
     already uses (`...priorEntry` semantics do not apply the same way
     here since this appends rather than replaces — but ensure the write
     as a whole still uses `updateDoc` with the full rebuilt `answers`
     array, matching the existing function's Firestore-write shape at
     `useQuizSession.ts:~2519-2560`).
4. **Fix the four consumers.** For each of `quizScoreboard.ts`,
   `questionAccuracyStats.ts`, `useQuizAssignments.ts`,
   `useVideoActivityAssignments.ts`: change the per-`questionId` selection
   logic from "first occurrence in array order" to:
   ```ts
   // Highest takeIndex wins; ties (same takeIndex — a race-created
   // duplicate, not a genuine retake) go to the earliest answeredAt,
   // preserving the original first-wins guard for that case.
   const winner = entriesForQuestion.reduce(
     (best, cur) => {
       if (!best) return cur;
       const bestIdx = best.takeIndex ?? 0;
       const curIdx = cur.takeIndex ?? 0;
       if (curIdx !== bestIdx) return curIdx > bestIdx ? cur : best;
       return cur.answeredAt < best.answeredAt ? cur : best;
     },
     undefined as QuizResponseAnswer | undefined
   );
   ```
   Entries with no `takeIndex` (every non-recording answer type) behave
   exactly as before — `takeIndex ?? 0` on a normal single-entry-per-
   question array is a no-op change. Add a comment at each site
   referencing this brief and the bugs (#1728/#1777) the original guard
   protected, so the next editor doesn't "simplify" it back to `.find()`.
5. **Fix (or verify already fixed) the absent-means-unanswered export
   sites.** Per §2's Phase-1-dependency note — check first, implement only
   if missing.
6. **Do not touch the results view or export's take-count display** — no
   UI work in this brief beyond the client-side "take N of takeLimit"
   affordance in the capture flow itself (brief 3.1's UI, extended here to
   show the budget). The teacher-facing take list/playback is brief 3.6.

## 5. Backward-compatibility constraints

- `takeIndex` and `takeLimit` are both optional/nullable. Every existing
  `QuizResponseAnswer` (no `takeIndex`) and every existing `recording`
  block (no `takeLimit`, or no `recording` block at all) must behave
  exactly as today.
- The four-consumer fix must be **semantically a no-op for every array
  that has zero or one entry per `questionId`** — which is every quiz in
  production today, since takes don't exist yet. Write a regression test
  proving this (see §6) before touching the logic.
- No Firestore rules changes. The append write must satisfy existing rules
  as-is; if it doesn't (e.g. some rule assumes replace-only semantics for
  `answers`), describe the needed change under "Protected-file change
  needed" rather than editing `firestore.rules`.
- No Storage/index changes — this brief is Firestore-array-shape and
  read-side logic only; upload/archival is 3.3.
