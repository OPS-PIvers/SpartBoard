# SpartBoard Chrome extension: web tours and focus sessions

Goal: one Chrome extension that does two things.

1. **Web tours (first).** Admins record live tours on any website (Schoology, Google Classroom, Infinite Campus, ...). A shared link opens the site and starts the tour.
2. **Focus sessions (later).** Keep students on allowed sites during a SpartBoard quiz or video activity, or during a teacher-started session on any website.

Scope was settled in a design interview with Paul on 2026-10-22, then revised the same day after an adversarial review against the code (review notes: `/mnt/project-files/chrome-extension/PLAN_REVIEW.md`, findings cited below as "Rn-#"). A second review against `dev-paul` at `9973eed` the same evening (`/mnt/project-files/chrome-extension/PLAN_REVIEW_2.md`, findings "R2-#") corrected the student identity, heartbeat, snapshot rule and managed-device gaps. This document is the contract.

**Code references** were taken at `dev-paul` commits `1da7f45` and `9973eed`. Symbol names are authoritative; line numbers are hints.

## Starting facts

- A live tour is a Guided Learning set with `mode === 'tour'` (`GuidedLearningMode`, `types.ts`). Each step carries `step.tour: GuidedLearningTourBinding`: an `anchor` from `config/tourAnchors.ts`, a `fallback {role, name}`, `action`, and SpartBoard-only fields (`value`, `teacherMustClick`, `slot`, `spawns`, `layoutKeyframes`, `unmapped`, `start`, `thumbnail {url, anchor, w, h}`). There is no CSS selector, URL or coordinate field.
- Drafts are at `building_guided_learning/{setId}`, readable by **any signed-in user, anonymous PIN sessions included** (`allow read: if signedIn()`); only `isAdmin()` writes. Published snapshots are at `building_guided_learning_tours/{setId}` (`components/tours/publishedTours.ts`), readable by `notAnon() && !isStudentRoleUser()`, which also admits a student who signs in through the teacher Google flow (no `hd` restriction in `config/firebase.ts`) or an email/password account; `isVerifiedDistrictEmail()` is the rule that means staff, with runs at `/runs/{uid}` whose rule `validRun` allows only `v, startedAt, furthest, done, exit, misses`.
- A published snapshot doc is `{set, publishedAt, publishedBy}`, read one doc at a time (`publishedTours.ts` `watchDoc`, `loadRunnableTour`), including the `_meta` marker and ids that were never published, so a read of a missing doc must keep succeeding. `glTourSnapshots` (`functions/src/glTours.ts`) deletes a snapshot when its `building_guided_learning` draft is deleted.
- Student sign-in is PII-free by design (`functions/src/studentIdentity.ts`): `studentLoginV1` verifies a Google Identity Services ID token, looks the student up in ClassLink and mints a custom token for an HMAC pseudonym uid with `studentRole`, `orgId` and `classIds`. The token carries no email, and email, name and sourcedId are never stored.
- Each write to a quiz response fires `gradeIndexQuizResponse`, `markPlcAssessmentDirtyOnResponse` and the attempt-history copy (`functions/src/quizAttemptHistory.ts`, `tabExits` is in `WATCHED_WHILE_DONE`), and updates every open live monitor. Video-activity responses fire `gradeIndexVideoResponse`.
- `storage.rules` already checks admins with `firestore.exists(.../admins/...)`, and `storage.cors.json` allows SDK `GET` reads from any origin.
- Tour pictures upload to the author's own `users/{uid}/hotspot_images/` (`hooks/useStorage.ts`) and are stored as Firebase download-token URLs. Anyone holding the URL can open them. There is no staff-only picture path.
- `LiveTourRunner` (`components/tours/LiveTourRunner.tsx`) only runs inside `DashboardView`. `findTourAnchor` (`components/tours/resolveTourAnchor.ts`) queries `[data-tour]` and falls back to ARIA role plus accessible name.
- Tours are authored in the on-board editor (`TourEditorHost` in `DashboardView`, `components/tours/editor/TourEditorPanel.tsx`, "Edit on board" in `components/widgets/GuidedLearning/Widget.tsx`), not in the Guided Learning Studio. The recorder (`components/widgets/GuidedLearning/components/recorder/`) captures pictures with `getDisplayMedia` and blurs `[data-pii]` elements.
- About 30 non-test files read `step.tour.anchor`, including `functions/src/mcp/glLiveTour.ts`, `tourDryRun.ts`, `tourPlaytest.ts`, `tourPictures.ts`, `components/tours/tourSelfHeal.ts`, `tourHealth.ts`, `tourSession.ts`, `scripts/snapshot-tour-anchors.mjs`, `audit-live-tours.mjs`, `run-live-tour.mjs` and `.claude/skills/gl-author/scripts/validate_gl_json.mjs`.
- `normalizeGuidedLearningSet` keeps unknown set and step fields, so a new field survives a re-save by an older client.
- Sharing today is `/help/{itemId}` plus `/r/help-...` short links (`components/help/helpCenterState.ts`). Admins can already create `short_links`.
- There is no fullscreen focus mode. Quizzes and video activities track tab-away with `hooks/useTabAwayTracker.ts` (listens to `blur` and `visibilitychange`), count `tabSwitchWarnings`, auto-submit at a threshold and record `tabExits[]` (max 50, append-only). `tabExitOk()` in `firestore.rules` allows only the keys `leftAt, returnedAt, durationMs, questionIndex, videoTime, attempt, outcome`, with `outcome` in `returned | over-limit | auto-submitted | session-ended`. Guided Learning and video-activity results views count `resultsTabWarnings`; mini apps track nothing.
- Iframe sandboxing is careful today: `srcDoc` iframes (mini apps, Embed code mode) never get `allow-same-origin`. Nothing enforces that.
- Root `tsconfig.json` excludes only `node_modules`, `dist`, `functions` and `remotion`; `eslint.config.js` ignores only `functions` and `remotion`. `check:tour-anchors` scans only `components/` and `App.tsx`.
- Students sign in to Google as `@students.orono.k12.mn.us`; staff as `@orono.k12.mn.us`. Prod Google sign-in to SpartBoard is Internal (Orono accounts only).
- No extension code exists in the repo. Orono runs no classroom-management tool (GoGuardian, Securly, etc.) on student Chromebooks.

## Decisions

### Shared

- **D1. One extension, tours first.** Web tours ship to staff first. Focus sessions are added later as a module of the same extension, and only after the counsel gate (G1).
- **D2. Private listing, force-installed by pilot OU first.** Publish to the Chrome Web Store as Private to the Orono Google Workspace. Force-install from Google Admin, starting with a **pilot OU** (Paul plus a test staff account, later a test student account), then the staff OU for tours, then students when Focus ships. The pilot OU stands in for "on for Paul first" for the extension itself, since a flag can't gate an installed extension (Rn-14). Users can't disable a force-installed extension.
- **D3. SpartBoard is the brain, and the extension trusts it narrowly.** The extension holds no Firebase login, token or SDK, and never reads or writes Firestore. A signed-in SpartBoard tab talks to it over `externally_connectable` messaging. Hard rules (Rn-3):
  - Accept messages only when `sender.origin` exactly matches a listed origin and `sender.frameId === 0`.
  - Validate every message against a schema; drop unknown types. Open only `https:` URLs.
  - Recording and screen capture start only from a button press in the side panel, never from a page message.
  - Content scripts never listen to `window.postMessage` and never trust the host page's DOM as instructions.
  - The extension never clicks, types, selects or submits on third-party sites. Web tour steps are observe-only for the extension; the learner acts. There is no Autopilot on web tours.
  - Tip text renders as text, never HTML.
  - Tour and record messages are refused unless the Chrome profile email (`chrome.identity.getProfileUserInfo({accountStatus: 'ANY'})`) is on `@orono.k12.mn.us`, so a student device never plays or records tours. A browser with no signed-in profile (a CBCM-enrolled PC used without signing in to Chrome) returns an empty email; `ping` reports that, and the hub uses the no-extension path (R2-6).
- **D4. Code lives in `extension/` in this repo.** It has its own Vite build (Manifest V3), its own `tsconfig.json` with Chrome types, and is excluded from the root `tsconfig.json`. It gets its own ESLint pass and lint-staged entry, the root Vitest include and the `test:counts` baseline, and `install:all` and CI install it. It imports types from `types.ts` and reuses the tour overlay components (`TourSpotlight`, `TourTip`, `TourBar`) inside a Shadow DOM. Those pull in `react-i18next`, Tailwind 3 classes from `lightChrome`, `Z_INDEX` and GL motion utils, so the extension initialises i18n, injects compiled Tailwind (preflight scoped to `:host`) into the shadow root, and builds the overlay CSS in px or scales it on `:host`, because a host page's root font size would rescale `rem` (Rn-13).
- **D5. Two extension IDs, one codebase.** A **prod** listing whose `externally_connectable.matches` lists only `https://spartboard.web.app/*` and `https://spartboard.firebaseapp.com/*`, and a **dev** listing (its own ID, Private, pilot OU only) that lists `https://spartboard-dev.web.app/*`, `https://spartboard-dev-bailey.web.app/*`, `https://spartboard-dev.firebaseapp.com/*` and `http://localhost:3000/*`-`http://localhost:3004/*`. Each host is listed exactly: Chrome only accepts `*.` as a leading subdomain wildcard and `web.app` is a public suffix, so `spartboard-dev*.web.app` is not a valid pattern. Hosting preview channels (`spartboard--*.web.app`) can't be matched and don't talk to the extension. The page picks the extension ID from its Vite environment; `vite-dev-prod` (localhost:3004, prod data) uses the dev ID (Rn-3, Rn-5).
- **D6. Protocol versioning.** `ping` returns `{protocol, version}`. The page uses only features the installed protocol supports and degrades to the no-extension path otherwise; the extension ignores message types it doesn't know. Protocol bumps are additive (Rn-5).
- **D7. Release pipeline.** CI builds and zips `extension/` on every PR. A push to `dev-paul` whose `extension/manifest.json` version changed publishes the **dev** listing. Publishing the **prod** listing runs from `main` behind a protected GitHub environment that needs Paul's approval, because there is no smoke test or rollback and a hotfix waits on Web Store review (Rn-5). Web Store API credentials live only in those GitHub environments' secrets. Self-hosting the dev build as a CRX (`update_url` on our hosting) is an allowed alternative if Web Store review slows dev testing; it only works on managed ChromeOS and CBCM-managed browsers.

### Managed-device setup (IT, one time)

- **M1. Publishing.** The Admin console allows users to publish private apps for the domain, and Paul registers a Chrome Web Store developer account on an Orono address. Confirm a Private listing is visible to the `@students.orono.k12.mn.us` domain and can be force-installed to the student OU before slice 13 (Rn-12).
- **M2. Staff browsers.** Force-install reaches Chromebooks, and Windows or Mac Chrome only when staff sign in to a managed Chrome profile or the browser is enrolled in Chrome Browser Cloud Management. Edge and Safari users get the T9 no-extension path (Rn-12).
- **M3. Student policies (before Focus).** Incognito off (user policy), guest browsing on the sign-in screen off (device policy), `DeveloperToolsAvailability` = blocked, `URLBlocklist` `javascript://*` so bookmarklets can't run on the SpartBoard origin, and `TaskManagerEndProcessEnabled` = false so a student can't end the extension's process from the ChromeOS Task Manager (Rn-1, Rn-12, R2-8).

### Web tours

- **T1. Same set, new surface.** A web tour stays a Guided Learning set with `mode: 'tour'` and a new set-level field `surface: 'spartboard' | 'web'` (missing means `'spartboard'`). Publishing to `building_guided_learning_tours`, snapshots and runs are reused. Drafts live elsewhere (T6), so `glBuildingIndexMirror` never sees them; the manager reads web tours from their own collection (T5).
- **T2. No mixed tours.** A tour is either a SpartBoard tour or a web tour. The Help Center, tour offers, What's New and `useTourOffers` skip `surface === 'web'`. The SpartBoard health view in `TourHealthPanel` skips them too; web tours get their own health section (T10).
- **T3. Web step binding is its own field.** Web steps carry `step.web: WebTourBinding` and no `step.tour`, instead of a union on a `kind` that may be missing, so every existing reader of `step.tour` keeps working unchanged and narrowing is exact (Rn-6). `WebTourBinding` holds:
  - `urlPattern`: origin plus path, with ids replaced by wildcards (T6).
  - `locator`: role plus accessible name, visible text, a short CSS path, the frame path, and the element's viewport position (tie-breaker only, T4).
  - `action` (observe / click / type / select) as a hint for the tip; the extension never performs it (D3).
  - `picture` (T6) and tip text.
- **T4. Layered locator with picture fallback.** Playback tries role+name, then text, then CSS path. Position never counts as a match on its own; it only breaks ties between candidates (Rn-11). If nothing matches, the step shows its picture with "Find this button". Each step reports which clue matched.
- **T5. Side-panel recorder, new web-step editor.** In a Chrome side panel the admin presses Record and clicks through the real site. Each click captures the locator and a screenshot (`chrome.tabs.captureVisibleTab`), scrolling the target into view first. Steps stream to the SpartBoard tab, which saves them as a draft. The on-board tour editor can't show web steps, so slice 8 adds a web-step list editor (wording, order, redaction, publish) in the Guided Learning manager's tour view, fed by an admin-only listener on `building_web_tours`, reusing `TourStepList` and the existing publish flow. `loadRunnableTour`'s fallback to `loadBuildingSet` never applies to web tours (Rn-6).
- **T6. Student data stays out of tours (Rn-2).**
  - Web-tour drafts live in a new admin-only collection, `building_web_tours/{setId}` (read and write `isAdmin()`), not in `building_guided_learning`, so anonymous and student sessions can't read them. Publishing writes the same `building_guided_learning_tours/{setId}` snapshot with a top-level `surface: 'web'` beside `set`. An `onDocumentWritten` trigger on `building_web_tours/{setId}` deletes that snapshot and the set's `web_tour_pictures/{setId}/` files when the draft is deleted, as `glTourSnapshots` does for SpartBoard tours.
  - The snapshot read rule becomes `staff() && (resource == null || resource.data.get('surface', 'spartboard') != 'web' || isVerifiedDistrictEmail())`. The `resource == null` arm keeps reads of unpublished ids and `_meta` succeeding, which `loadRunnableTour` and every launch point rely on; without it those reads fail for everyone and SpartBoard tours stop resolving (R2-3). Rules tests cover a staff read of a missing doc, a SpartBoard snapshot read by a non-district account, and a web snapshot read by staff, by a `@students` Google account and by an anonymous user.
  - Pictures go to a new Storage path, `web_tour_pictures/{setId}/{file}`, with `get` for verified district staff (add an `isVerifiedDistrictEmail()` helper to storage.rules, which has only `isAdmin()` today) and `list`, write and delete for admins (the existing `isAdmin()` there). The client reads them through the SDK (`getBytes`), never stored download-token URLs. The web-step editor deletes the picture of a step it removes when the draft is saved, so pictures don't outlive their steps (R2-4).
  - The recorder crops pictures to the target and its surroundings, and the side panel has a blur-region tool.
  - The recorder replaces digit runs, UUIDs and query values in `urlPattern` with wildcards by default, and shows every captured text field (name, text, CSS path, URL) in the editor with a redact control.
  - Publishing is blocked until the admin ticks "I checked this step for student data" on every step, covering the picture, the captured text and the page address.
- **T7. Multi-page tours in one tab.** Each step stores its `urlPattern`. The service worker keeps tour progress per tab in `chrome.storage.session` and re-injects the overlay on `webNavigation.onCommitted` (new documents and new frames) and `onHistoryStateUpdated` (in-app route changes), then waits for the expected page before showing the step (Rn-11). New tabs and popups are a v2 question.
- **T8. Host access: any site, inject on demand.** The manifest declares `<all_urls>` but ships no always-on content scripts. The extension injects with `chrome.scripting.executeScript` (all frames) only into a tab that is playing or recording a tour, and reads nothing on any other site. Every frame gets only a small locator script; the React overlay bundle (D4) is injected into the frame holding the matched target, so a page built from many frames doesn't load React, i18n and Tailwind in each one (R2-7). Focus sessions (F1) also read the top-level address of every tab on a student device while a session runs, keeping only its domain (F4); the `/privacy` section says so. IT can still block hosts in Google Admin (`runtime_blocked_hosts`).
- **T9. `/tour/{setId}` page is the hub.** Shared links are `/tour/{setId}`, with `/r/tour-...` short links (extend the `helpShortLinkCode` family). The route mounts only auth and the published-tour read, not the dashboard. The page:
  - With the extension: opens the tour's start URL in a new tab, hands the tour over (the hub fetches each step's picture through the SDK and passes the bytes, capped per message, since the extension can't read Storage), and stays open as the tour's home with a step checklist. It receives progress over a runtime port and writes the run doc.
  - Without the extension (or an older protocol, D6): shows the tour as picture steps and says how to get the extension.
  - If the site tab is closed, the tour can be resumed from here.
- **T10. Web tour health.** The run doc gains optional `surface`, `weak` (per-step clue that matched, list ≤ 50) and keeps `misses`. `validRun` is extended for them, with rules tests for reads and writes. A "Web tours" section in Live tour health shows misses and weak matches per step (Rn-7).
- **T11. Discovery is links only in v1.** Admins manage web tours in the Guided Learning manager, filtered by surface, and share links in email, Schoology and newsletters.
- **T12. Flag.** New `GlobalFeature` `web-tours`, a `FEATURE_DEFAULTS` entry (`defaultAccessLevel: 'admin'`, `defaultEnabled: true`, `missingDocPublic: false`, `stage: 'preview'`, `afterLaunch: 'keep'`, `category: 'integrations'`, plus `label`, `icon` and `description`), also added to `functions/src/featureMissingDoc.ts`. It gates authoring (the "Web tour" option, the recorder hand-off, the side panel) and the `/tour/{setId}` route. The installed extension is gated by the pilot OU (D2). Because the flag gates the route, a pilot teacher who isn't an admin goes on the flag's Beta users list as well as the pilot OU (R2-9).
- **T13. Existing tooling refuses web tours until it supports them.** Web tours reach code that reads published snapshots or looks a set up by id, not code that scans `building_guided_learning` drafts. So the readers of `building_guided_learning_tours` and set-id lookups (the connector's `glLiveTour.ts`, `tourDryRun.ts`, `tourPlaytest.ts`, `tourPictures.ts`; `LiveTourRunner`, self-heal, `tourHealth`, `useTourOffers`, `run-live-tour.mjs`) skip or reject `surface: 'web'`, each with a test. Draft scanners (`snapshot-tour-anchors.mjs`, `audit-live-tours.mjs`, the gl-author validator) need no change (Rn-6).

### Focus sessions

- **F0. Counsel gate first.** Logging where students browse on school-issued devices likely falls under Minnesota's 2022 school-issued device law (believed to be Minn. Stat. 13.32, subd. 14), which limits monitoring to listed exceptions such as instruction or exam proctoring and requires advance notice to families. Before any Focus code merges, counsel reviews F1-F10 and the family notice, and the `/privacy` extension section gains F4 (Rn-4). The T8 part of that section ships earlier, in slice 3, for store review (R4). Paul owns this gate (G1).
- **F1. One engine, two entry points.** The extension runs a "focus session": an allowlist plus an enforcement level.
  - (a) A quiz or video activity with tab-away tracking on starts one automatically, with the allowlist set to that activity and the enforcement level taken from a new session option, `focusLevel`, beside `tabAwayLimitSeconds` in `BaseSessionOptions` (`types.ts`). It is set in the assign flow behind `focus-sessions`, with a `tourAttr` anchor, and missing means Redirect (R2-10).
  - (b) A teacher starts a standalone session on any sites from a new **Focus** widget.
    Both record exits in the existing `tabExits` shape. Standalone sessions get their own session/response collection, with rules modelled on the video-activity response rules.
- **F2. Teacher picks enforcement.** Per session: **Monitor** (allow and log), **Redirect** (send the student back to the allowed tab with a notice, and log it; the default), or **Lock** (block non-allowed navigation, and close tabs and windows the student opens). Requires the M3 policies.
- **F3. Signed grants; the student's tab only keeps the session alive (Rn-1).** A callable (`focusGrantV1`) checks the caller is the teacher of the session (or, for F1a, that the student has an open response on that activity) and returns a grant signed with an ECDSA P-256 key held in Secret Manager in both projects: `{kid, sessionId, seq, studentUid, emailHash, allowlist, level, expiresAt}`. P-256, not Ed25519, because WebCrypto Ed25519 needs Chrome 137 and student Chromebooks can sit on an older LTS release; the manifest sets `minimum_chrome_version` to 116, the side panel's floor (R2-5). The extension verifies grants with the public keys built into each listing (keyed by `kid`, so a key can be rotated by shipping the new public key one release before signing with it) and:
  - rejects a grant whose `emailHash` isn't `SHA-256(sessionId + ':' + profile email)` for the Chrome profile (`chrome.identity.getProfileUserInfo({accountStatus: 'ANY'})`, `identity.email` permission), so a grant can't be used on another student's device. Student tokens carry no email by design (Starting facts), so the server learns it the way sign-in does: `studentLoginV1` also stores `emailTag = HMAC(STUDENT_PSEUDONYM_HMAC_SECRET, 'emailtag:' + lowercased email)` (its own prefix, apart from the uid's `sid:`) in `student_sections/{uid}`, on both the ClassLink path and the dev mock-class (`testClasses`) path, in the same write as `sectionIds`. `focusGrantV1` takes a fresh GIS ID token from the student's page for the first grant of a session, verifies it as `studentLoginV1` does, and issues the grant only when its email's tag matches the caller's stored tag. Renewals (higher `seq`) need no new ID token: the server checks `sessionId` and `studentUid` and never extends past the first grant's `expiresAt`, because a hidden tab can't answer a GIS prompt. The email itself is never stored, logged or put in a grant. The tag is pseudonymous personal data (an email is guessable, so anyone with the secret could test one), and counsel reviews it with F1-F10; the fallback, if counsel says no, is a ClassLink lookup per first grant comparing `computeStudentUid` with the caller (R2-1). A student with no tag (signed in before it existed, or the write failed) gets no grant and is treated like a PIN join until their next sign-in;
  - holds one active session and accepts only a grant for that `sessionId` with a higher `seq`, or a new session after a signed end or the active grant's `expiresAt`, so an older or looser grant can't be replayed;
  - accepts a start, allowlist change or end only inside a valid grant;
  - lets a teacher-started standalone grant (F1b) supersede an active F1a session; the superseded activity's page gets a `superseded` notice and goes back to today's tracker. A new F1a grant never supersedes a standalone session; that activity also keeps today's tracker.
    Ends are signed too: the teacher ending the session, or the server when it records the quiz or video-activity submission, issues a signed end the student's page relays. For F1a the server derives the allowlist and level from the activity, never from the request. A student with no Google email (anonymous PIN join) gets no grant: the hand-off is refused, today's tracker keeps running, and the roster shows "not enforced (PIN join)". The student's SpartBoard tab (joined through the normal ClassLink or join-code flow) relays grants, renews the lease and writes exit events; it can't widen the allowlist or end Lock. Closing it counts as an exit and the extension reopens it. The extension never holds student credentials.
- **F4. Domain and time only.** The teacher sees the domain the student went to and how long they were away. Never full URLs, page titles or content. `tabExitOk()` gains an optional `domain` string (so a teacher's already-open tab running the previous client still passes) and the outcome `redirected`. The log stops at 50 entries; after that, exits only raise an optional `tabExitsOverflow` counter (rules: may only increase), and the roster shows "50+ exits".
- **F5. Lease plus hard cap.** The extension keeps the heartbeat on its side (`chrome.alarms` plus an open port to the student's tab) and sets `autoDiscardable: false` on that tab, so a low-memory Chromebook discarding a hidden tab or Chrome throttling its timers doesn't end the session (Rn-9). The session ends when the teacher ends it, when the quiz or video activity is submitted, at the grant's `expiresAt` (at most 90 minutes), or 2 minutes after the tab is gone and can't be reopened. A rebooted or offline Chromebook always comes back unlocked. Nobody is left to write an exit in those cases, so the service worker's 30-second alarm sends a beat over the port and the student's tab writes a heartbeat timestamp at most once a minute to its own small doc, `{session collection}/{sessionId}/focus/{responseKey}`, never to the response: each response write fires two or three functions and every open live monitor, and a 30-second heartbeat on the response would be thousands of trigger runs per class period (R2-2). Rules let a student write only their own heartbeat doc and the teacher read them, and no trigger watches that path. The roster shows a student whose heartbeat is older than 3 minutes as "focus lost" until it resumes, leaving margin for a throttled hidden tab.
- **F6. Focus widget.** New `focus` widget through the `new-widget` skill. The teacher picks a class, adds allowed sites (or pulls them from the board's URL and Embed widgets), picks the enforcement level, sets a time limit and starts. It shows a live roster with who is away, where (domain) and for how long. It ships at `feature_permissions` access level `admin`.
- **F7. One source of exits (Rn-8).** While an extension session is active for an activity, the extension is the only source of exit events: `useTabAwayTracker` takes its leave and return events from the extension instead of `blur` and `visibilitychange`, so a redirect or an extension notice taking focus isn't counted twice. The tracker's three stops still run on those events: the warning threshold (as below), the away-time limit (`tabAwayLimit`, `limitMs`/`onAwayTooLong`, outcome `over-limit`) in every mode, and the post-unlock submit on the next exit in every mode. Exits count toward `tabSwitchWarnings` and the auto-submit threshold only in Monitor mode; in Redirect and Lock, redirected or blocked exits are logged but never auto-submit. With no extension (F8), or with `focus-sessions` off, today's tracker runs unchanged, and its existing tests pass unmodified.
- **F8. No extension means fall back and flag it.** Quizzes and video activities fall back to today's browser-only tab-away tracking. A standalone session still opens the allowed sites but can't enforce them. Either way, the roster marks the student "not enforced (no extension)", using `ping` (D6).
- **F9. Allowlist matching (Rn-10).** Each entry is parsed into a host (exact, or a subdomain at a dot boundary) plus a path prefix; never a string prefix. Google Docs, Drive and Classroom get rules that accept `/u/N/` and the `/edit`, `/view` and `/preview` forms of the same file. Unit tests cover lookalike hosts (`desmos.com.evil.example`). Sign-in and SpartBoard hosts are always allowed (`accounts.google.com`, `launchpad.classlink.com`, and every SpartBoard origin in that listing's `externally_connectable` list from D5), so logging in never counts as an exit. Only top-level navigations are checked: frames inside an allowed page (YouTube in a video activity, a Desmos embed) are not. Lock blocks non-allowed `main_frame` requests with `declarativeNetRequest` session rules, a permission slice 12 adds, which means a new store review for that release, and closes tabs and windows the student opens with `chrome.tabs.onCreated` and `chrome.windows.onCreated`, since request blocking can't stop a blank new tab (R2-8).
- **F10. Flag.** New `GlobalFeature` `focus-sessions` with the same `FEATURE_DEFAULTS` shape as T12 (`afterLaunch: 'keep'`, `category: 'students'`, plus `label`, `icon` and `description`), also added to `functions/src/featureMissingDoc.ts`. It gates the automatic quiz and video-activity hand-off (F1a). The Focus widget is gated by its `feature_permissions` record.

## Risks, in the order to prove them

- **R1. Frames and in-app navigation.** Schoology, Google Drive and Infinite Campus build pages from frames on other origins, and single-page apps change route without navigating. The extension injects into every frame, re-injects into frames added later, records each target's frame path and draws the spotlight in the right frame. **Prove this first** (slice 1).
- **R2. Service worker lifetime.** MV3 service workers stop when idle. Tour progress and focus leases live in `chrome.storage.session` and `chrome.alarms`, never in memory.
- **R3. Screenshots only cover the viewport.** `captureVisibleTab` captures what's on screen, so the recorder scrolls the target into view before capturing, and the prototype checks it captures content inside cross-origin frames.
- **R3b. Host page security policies.** Google Classroom and Drive send strict CSP and Trusted Types. The prototype checks that the overlay's styles, fonts and the picture fallback (bytes shown as `blob:` or `data:` images) render under each site's policies; if one blocks them, the picture fallback opens in an extension page instead (R2-7).
- **R4. Store review for `<all_urls>`.** A Private listing still goes through review, which can take days. The listing links the `/privacy` extension section.
- **R5. Limits of focus mode.** It can't stop another device, another Chrome profile, Android apps, installed web apps in their own windows or ChromeOS system apps. Lock only holds while the M3 policies are set. Teacher-facing copy must say so.
